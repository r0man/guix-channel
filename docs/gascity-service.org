#+title: The Gas City service
#+options: toc:2

This manual documents the Gas City service shipped by the =r0man= Guix
channel: the system service =gascity-service-type=, the derived home service
=home-gascity-service-type=, and the Guix record surface that compiles to Gas
City's =city.toml=, =pack.toml= and =supervisor.toml=.  Gas City itself is
documented at <https://github.com/gastownhall/gascity>.

The service layers:

- =gascity-service-type= (=r0man guix services gascity=) — runs one or more
  machine-wide Gas City supervisors (=gc supervisor run=) as daemons, each in
  its own =GC_HOME=.
- =home-gascity-service-type= (=r0man guix home services gascity=) — the user
  counterpart, running supervisors under =$HOME/.gc= as the user who owns the
  Home environment.  It re-exports every record and accessor of the system
  module, so a Home configuration needs only the home module import.
- =r0man guix toml= — the TOML intermediate representation and emitter the
  serializers build on, and the constructors the =extra-config= escape hatch
  uses.
- =r0man guix services gascity records= — the *generated* leaf-record surface,
  produced from the committed Gas City JSON schemas.  See [[#generated-records]].

* Overview

** The service value is a list of supervisors

The value of =gascity-service-type= is a =list= of
=<gascity-supervisor-configuration>= records, one per supervisor process (the
same shape as =github-actions-runner-service-type=).  A single-element list is
the common case; =gascity-service-config= builds it for you:

#+begin_src scheme
(service gascity-service-type
         (gascity-service-config
          (cities (list (gascity-city-configuration
                         (name "swarm"))))))
#+end_src

Pass a plain =list= when you want more than one supervisor.  Each record may
also carry a list of cities; =gascity-service-config= is just sugar for a
one-element list.

** GC_HOME isolation

Gas City isolates supervisors by =GC_HOME=: the registry (=cities.toml=), the
settings (=supervisor.toml=), the control socket, the instance lock and the
runtime/events state all live under it.  The service pins =GC_HOME= *and*
=XDG_RUNTIME_DIR= to each instance's =gc-home=, so an isolated supervisor never
touches the host supervisor's socket or lock.

| Concern | Path | Isolated by |
|---------+------+-------------|
| city registry | =$GC_HOME/cities.toml= | =gc-home= |
| supervisor settings | =$GC_HOME/supervisor.toml= | =gc-home= |
| control socket / lock | =$GC_HOME/supervisor.{sock,lock}= | =gc-home= |
| API listener | =bind=:=port= | =port= (must be distinct) |
| per-city tmux server | =tmux -L <city-name>= | city name / =[session].socket= |
| per-city Dolt | port hashed from the city path | city path |

Two instances that share a =gc-home= or a =(bind, port)= fail closed at
evaluation.  A lone instance defaults to port =8372=; every instance of a
multi-instance service must set =port= explicitly.  A system supervisor and a
home supervisor on the same host share the network namespace, so they too need
distinct ports.

** Dolt author identity
:PROPERTIES:
:CUSTOM_ID: dolt-identity
:END:

=gc init= of a managed bd store runs Dolt's =init=, which commits a bootstrap
revision and therefore needs a commit author identity.  Dolt reads it from
=$DOLT_ROOT_PATH/.dolt/config_global.json= (or =$HOME/.dolt=) and fails at
genesis when it is absent, so the provision one-shot fails and the supervisor
never starts.  The root activation (not the one-shot) materializes
=<state-directory>/.dolt/config_global.json= (=0600=, owned by the service
user):

| Field | Default |
|-------+---------|
| =dolt-user-name= | =Gas City= |
| =dolt-user-email= | =gascity@localhost= |

- Setting *either* field is explicit intent: the file is rewritten, the unset
  field filled with the default above.
- When *both* are unset the default identity is written only if no file exists
  yet; an existing file (an operator- or sops-provided identity) is left
  untouched, so the service never clobbers it.
- The write is compare-and-write, so an unchanged reconfigure does not touch
  the file.

The service user's home is the state directory, so =$HOME= and
=$DOLT_ROOT_PATH= both point at it; the provision one-shot and the supervisor
environment pin =DOLT_ROOT_PATH= explicitly.  This is service configuration,
not a Gas City TOML key: it is never emitted into =city.toml= or
=supervisor.toml=.

** Multiple cities

One supervisor manages a list of cities.  Each city owns a directory, its
generated =city.toml=/=pack.toml=, its =files=, and its registration in the
instance's =cities.toml=.  City names must be unique per supervisor (they become
the tmux socket names); distinct supervisors may manage disjoint or disjointly
named cities.

#+begin_src scheme
(service gascity-service-type
         (gascity-service-config
          (cities (list (gascity-city-configuration
                         (name "burningswell")
                         (directory "/var/lib/gascity/burningswell"))
                        (gascity-city-configuration
                         (name "sandbox")
                         (directory "/var/lib/gascity/sandbox"))))))
#+end_src

* Gas City docs -> Guix records

Every record's accessor is named =gascity-<record>-<field>=, and the field is
the TOML key with =_= replaced by =-=.  Declaration order in the record is
emission order in the generated TOML.

** Field-type conventions

| Convention | Scheme type | Emission |
|------------+-------------+----------|
| optional scalar | ='unset= | nothing |
| optional string | string or ='unset= | =key = "value"= |
| maybe-string-or-gexp | string, gexp or ='unset= | =key = "..."=, gexp spliced verbatim between the quotes |
| tri-state boolean | ='unset=, =#t= or =#f= | nothing, =true= or =false= |
| maybe boolean | ='unset=, =#t= or =#f= | nothing, =true= or =false= |
| integer / real | exact / inexact number or ='unset= | decimal |
| list of strings | Scheme list, default ='()= | =key = ["a", "b"]= |
| string map | alist ='(("K" . "v") ...)= | =key = { K = "v", ... }= |

- ='unset= is the absent marker; an absent field emits nothing, so Gas City
  applies its own default.  This is what makes tri-state booleans and
  presence-aware patches work.
- Predicates =gascity-tri-state?=, =gascity-maybe-string?= and
  =gascity-maybe-string-or-gexp?= test these shapes.
- Strings that may embed a store path (commands, scripts) are typed
  =maybe-string-or-gexp=: a gexp is a first-class TOML value kind and is spliced
  verbatim between the surrounding quotes.  Only literal fragments are escaped
  at build time; a spliced gexp must not need further escaping.
- Array tables that Gas City spells in the singular (=[[agent]]=,
  =[[named_session]]=, =[[rigs]]=) get a *plural* record field (=agents=,
  =named-sessions=, =rigs=); the TOML key is unchanged.
- Maps keyed by a name (=providers=, =upstreams=, =imports=, and the pack's
  =runtimes=) are alists of =(name . record)=, e.g.
  =(providers (list (cons "claude" (gascity-provider-configuration ...))))=.

** The generated leaf records

Every documented field of Gas City's =City= and =Pack= schemas is mirrored by a
*generated* leaf record in =modules/r0man/guix/services/gascity/records.scm=,
module =(r0man guix services gascity records)=.  That file is generated from the
committed schemas =docs/reference/schema/{city,pack}-schema.json= by
=scripts/generate-gascity-records.scm=; regenerate it with =make
generate-gascity-records= and check it with =make check-gascity-records=.  Do
not edit it by hand.

The generated records follow the same conventions: the module is
=(r0man guix services gascity records)=, each record is
=<gascity-<name>-configuration>= with =gascity-<name>-configuration-<field>=
accessors, every field defaults to ='unset=, and the leaf records whose
hand-written sibling lives in =gascity.scm= exist in both (the hand-written one
is the Phase-2 subset the service itself needs).  When you need a field the
hand-written records do not expose, import the generated module, or reach the
key through =extra-config=.

* Worked examples

All examples below are the shapes the test suite renders verbatim
(=tests/r0man/guix/services/gascity.scm=), so they are known to match the
implemented API.

** City: the swarm example

Gas City docs:

#+begin_src toml
[workspace]
name = "swarm"
provider = "claude"

[providers.claude]
base = "builtin:claude"

[daemon]
patrol_interval = "30s"
max_restarts = 5
restart_window = "1h"
shutdown_timeout = "5s"

[[rigs]]
name = "checkout-service"
prefix = "cs"
formula_vars = { push = "true", open_pr = "true", drain_policy = "separate" }
#+end_src

Guix records:

#+begin_src scheme
(gascity-city-configuration
 (name "swarm")
 (directory "/var/lib/gascity/swarm")
 (workspace (gascity-workspace-configuration
             (name "swarm")
             (provider "claude")))
 (providers
  (list (cons "claude"
              (gascity-provider-configuration (base "builtin:claude")))))
 (daemon (gascity-daemon-configuration
          (patrol-interval "30s")
          (max-restarts 5)
          (restart-window "1h")
          (shutdown-timeout "5s")))
 (rigs (list (gascity-rig-configuration
              (name "checkout-service")
              (prefix "cs")
              (formula-vars '(("push" . "true")
                              ("open_pr" . "true")
                              ("drain_policy" . "separate")))))))
#+end_src

** extra-config (structured escape hatch)

=extra-config= is a list of TOML IR nodes layered over the generated document
*before* emission: a field at the same full TOML key *replaces* the generated
field, and a table *merges recursively*.  A key declared twice inside
=extra-config= at one level is an error.  Build the nodes with the
=(r0man guix toml)= constructors =toml-table=, =toml-field=,
=toml-array-of-tables=, =toml-inline-table= and =toml-array=; keys may be
symbols or strings.

#+begin_src scheme
(gascity-city-configuration
 (name "experiment")
 (extra-config
  (list (toml-table 'experimental
                    (toml-field 'feature_flag "true")))))
;; => [experimental]
;;    feature_flag = "true"
#+end_src

Overriding a generated field:

#+begin_src scheme
(gascity-city-configuration
 (name "m")
 (workspace (gascity-workspace-configuration
             (name "a")
             (provider "claude")))
 (extra-config (list (toml-table "workspace" (toml-field "name" "b")))))
;; => [workspace]
;;    name = "b"
;;    provider = "claude"
#+end_src

** extra-toml (raw append)

=extra-toml= is a string or a =file-like= appended verbatim at the end of the
generated file.  It can only add whole new tables: a verbatim append cannot add
a root-level scalar after a table header, nor extend a table the generator
already emitted (that would be a duplicate-table error).

#+begin_src scheme
(gascity-city-configuration
 (name "t")
 (workspace (gascity-workspace-configuration (name "t")))
 (extra-toml "[extra_table]\nk = 1\n"))
#+end_src

** files and rig-files

=files= is a list of =(destination . file-like)= pairs copied into the city
root; =rig-files= into each declared rig root.  Both are data only: they are
never emitted to TOML.  This is how prompt templates, formulas, orders, skills,
=.mcp.json=, scripts and overlays are supplied.

#+begin_src scheme
(gascity-city-configuration
 (name "burningswell")
 (files (list (cons "prompts/mayor.md" (plain-file "mayor.md" "You are the mayor."))
              (cons ".mcp.json" (local-file "city/.mcp.json"))))
 (rig-files (list (cons "scripts/gate.sh" (local-file "gates/gate.sh")))))
#+end_src

Destinations are relative to the root and may not escape it (no empty, =.= or
=..= components; a lone ="."= names the root itself, for a directory source),
may not be declared twice, and may not name a file the service writes itself
(=city.toml=, =pack.toml=, =.gc/site.toml=; a file of a directory source that
would land there is skipped with a warning).  A source is one of:

- a file-like object, or an absolute file name, naming a *file*: copied to
  the destination, mode =0755= when the source is executable and =0644=
  otherwise;
- a file-like object, or an absolute file name, naming a *directory*: every
  file below it is copied below the destination the same way, so a whole pack
  tree ships as one =(local-file "city" #:recursive? #t)=;
- =(gascity-symlink TARGET)=: the destination becomes a symbolic link to
  TARGET, a string or a file-like object such as a =file-append= into a
  package (for helpers that must resolve files relative to their own location).

#+begin_src scheme
(gascity-city-configuration
 (name "burningswell")
 (files (list (cons "." (local-file "gascity" "city-pack" #:recursive? #t))))
 (rig-files
  (list (cons ".gc/scripts/checks" (file-append packs "/gascity/assets/scripts/checks"))
        (cons ".gc/scripts/artifacts.py"
              (gascity-symlink
               (file-append packs "/gascity/assets/scripts/artifacts.py"))))))
#+end_src

Each activation converges every root to its entries: a file that already
matches is left alone, a changed or read-only copy is replaced atomically, a
drifted mode is repaired, and a symbolic link in place of a file is replaced
by the file.  A directory in place of an entry is never replaced (the
activation logs it and goes on).

The managed paths of each root are recorded in =.gc/gascity-files.manifest=
below it.  An entry a later generation no longer declares is removed, with the
directories it leaves empty; files the service did not install (a log an
order writes, a note an agent leaves) are never touched.  When a removed file
was a formula, the links =gc= staged for it in =.beads/formulas/= of the city
and its rigs would dangle until =gc= rebuilds that directory, so the
activation removes those links too.

* Running the examples

The channel ships two runnable example configurations, one per service, each
running a single supervisor with one trivial =swarm= city.  Both use the
service defaults, so neither hardcodes the host's =$HOME= or a state path.

- =examples/gascity/home.scm= — a =home-environment= using
  =home-gascity-service-type=.  Build it, or run its activation and a command
  in a container:

  #+begin_src sh
  guix home build -L modules examples/gascity/home.scm
  guix home container -L modules examples/gascity/home.scm -- gc --version
  #+end_src

  The state and log directories default to =$XDG_STATE_HOME/gascity= and
  =GC_HOME= to =$HOME/.gc=.

- =examples/gascity/system.scm= — an =operating-system= using
  =gascity-service-type=, in the style of =simple-operating-system=.  Build a
  VM or a container:

  #+begin_src sh
  guix system build -L modules examples/gascity/system.scm
  guix system vm -L modules examples/gascity/system.scm
  guix system container -L modules examples/gascity/system.scm
  #+end_src

  The supervisor runs as the =gascity= account, with state under
  =/var/lib/gascity=.  The serial console is architecture-dependent: the
  example selects =ttyAMA0= on aarch64 (where QEMU's =virt= machine wires its
  PL011 UART), so on aarch64 the generated =guix system vm= launcher needs
  QEMU's machine and CPU, =$(guix system vm -L modules examples/gascity/system.scm)
  -M virt -cpu max=, while on x86_64 =guix system vm -L modules
  examples/gascity/system.scm= works as-is.

- =examples/gascity/github-app.scm= and
  =examples/gascity/github-machine-user.scm= — the same system service,
  committing as a GitHub App or as a machine user; see [[*GitHub identity]].
  Replace the placeholder App, identity and secret paths before booting them:

  #+begin_src sh
  guix system build -L modules examples/gascity/github-app.scm
  guix system build -L modules examples/gascity/github-machine-user.scm
  #+end_src

=scripts/gascity-container-smoke-test= wraps the image invocations:

#+begin_src sh
scripts/gascity-container-smoke-test home     # Home activation and generated TOML
scripts/gascity-container-smoke-test system   # machine-wide lifecycle
scripts/gascity-container-smoke-test all      # both, in that order
#+end_src

The =home= check builds =examples/gascity/home.scm= with
=guix home container=, runs the Home activation, and asserts in the container
that the state directory and the generated =city.toml=, =pack.toml= and
=supervisor.toml= exist and contain the expected keys, then runs
=gc config show --validate= in the generated city directory (skipping
gracefully if =gc= is unavailable).  It prints =PASS= or =FAIL: reason= and
exits non-zero on failure.  Because =guix home container= never starts
=home-shepherd-service-type=, the provision one-shot (genesis, site binding,
registry) and the running user shepherd are not covered here; the unit tests
cover them, and the =system= check covers the machine-wide path.

The =system= check builds =tests/r0man/guix/services/gascity-container.scm=, a
test-only =operating-system= that mirrors =examples/gascity/system.scm= and adds
a one-shot assertion service.  It boots the OS's real shepherd (PID 1), so the
full machine-wide lifecycle runs: activation materializes =city.toml= and
=pack.toml=, the provision one-shot runs genesis and registers the city, and
=gc supervisor run= is running as the =gascity= account.  The assertion service
waits (bounded) for =supervisor.sock= and =cities.toml=, then checks that
=city.toml=, =pack.toml=, the =.gc/site.toml= site binding and the =cities.toml=
registry exist, that the =gascity-supervisor= service is running, that the
state is owned by the =gascity= account, and finally that
=gc config show --validate= accepts the generated city.  It writes =PASS= or
=FAIL: reason= into a host directory shared with =--share=, and the script maps
that to =PASS: system= or a non-zero exit.  The image never shuts down by
itself: the script polls the shared directory for the verdict under a hard
timeout, then tears the image down and kills its process group.

The =system= check prefers =guix system container=, which boots the shepherd
without emulation.  That path requires mapping a 65536-uid/gid range into the
container's user namespace, which the kernel permits only for root (Guix does
not use =newuidmap=); on an unprivileged host the container exits at once with
=EPERM=, so the script falls back to =guix system vm --no-graphic=.  The VM
boots the very same OS with the same assertions and needs no privileges (QEMU
is used, with KVM when available).  The =system= section of
=tests/r0man/guix/services/gascity-container.scm= documents that fallback.

The checks are also available as opt-in make targets.  They are deliberately
NOT part of =make check=, as they need the Guix daemon and, for the VM
fallback, QEMU:

#+begin_src sh
make check-gascity-home-container     # scripts/gascity-container-smoke-test home
make check-gascity-system-container   # scripts/gascity-container-smoke-test system
make check-gascity-containers         # scripts/gascity-container-smoke-test all
#+end_src

* Interactive container demo

The =bright-lights= example,
=examples/gascity/bright-lights-home.scm=, is a runnable Home environment for
the [[https://github.com/gastownhall/gascity][Gas City]] quickstart: one
supervisor running a fresh city called =bright-lights= with the builtin
=claude= provider.  It puts =claude-code= on both the supervisor's agent
=PATH= (so =gc sling= can spawn a claude agent) and the interactive user's
=PATH=, and shares the host Claude Code state so an existing login keeps
working inside the container.

=scripts/gascity-home-container= wraps the invocation.  It builds and runs the
example with =guix home container=, waits (bounded) for
=home-gascity-supervisor= to reach =Started=, prints a short banner and drops
you into a login shell:

#+begin_src sh
scripts/gascity-home-container
#+end_src

The banner tells you the city directory and =GC_HOME=, and the commands that
matter inside the shell:

#+begin_src sh
gc status                                # supervisor and city status
cd ~/my-project && gc sling my-project/claude "your task"
#+end_src

The example declares the tutorial's project rig =my-project= (=~ /my-project=)
with prefix =mp=, so =gc sling my-project/claude ...= has a target out of the
box; the wrapper runs the idempotent =gc rig add ~/my-project= before dropping
you into the shell (the controller may not have finished initializing a
declared rig's beads yet).  It does not call the Anthropic API itself.

** Container workarounds

=guix home container= leaves two gaps the wrapper/example close so agent
sessions actually start:

- =devpts= is mounted with =ptmxmode=000=, so =/dev/ptmx= is unopenable and
tmux cannot allocate a PTY ("create window failed: fork failed: Permission
denied").  A remount needs =CAP_SYS_ADMIN=, which the unprivileged container
lacks, but the container user owns the node, so the wrapper =chmod=s
=/dev/pts/ptmx= to =0666=.
- The supervisor's =HOME= is the state directory, not the user's home, so
claude misses the shared =~/.claude= ("Not logged in") and =~/.claude.json=
(and hangs at the first-run theme prompt).  The example's Home activation
links both into the state home before the supervisor starts.

** What the container shares

- =$HOME/.claude= and, when present, =$HOME/.claude.json= are mounted
  *read-write* (=--share=), so the container reuses the host's Claude Code
  credentials.  Only Claude Code itself writes there.  *The container is
trusted and local:* it can read and write your Claude Code state, so run it
  only on your own machine.
- The host =/bin= is exposed (=--expose=/bin=/bin=).  =guix home container=
  provides no =/bin= at all, but the generated bead shim (=gc-beads-bd.sh=) is
  =#!/bin/sh= and the login shell is =bash=; without it the provision one-shot
  cannot start Dolt and the supervisor never comes up.
- The container accesses the *network* (=--network=), which =claude= needs.

** The city is ephemeral

The state directory is pinned to =$HOME/.local/state/gascity=, =GC_HOME= to
=$HOME/.gc=, and =guix home container= mounts a volatile tmpfs over =$HOME=.
The whole city therefore lives inside the container and is discarded when you
exit: nothing is written to the host home except what Claude Code itself
writes under the shared =~/.claude=.

The demo also shares the host *network namespace* (required for =claude=),
and a machine-wide supervisor already owns the default API port =8372=, so the
example binds =18372= instead.  Override it with =GASCITY_DEMO_PORT= when the
host already uses that port.

** Non-interactive use

A command after =--= runs in the container instead of the login shell (still
after the wait) and its exit status is propagated; =GASCITY_DEMO_CMD= does the
same with a single command line.  Both are what the non-interactive checks
use:

#+begin_src sh
scripts/gascity-home-container -- gc status
scripts/gascity-home-container -- sh -c 'gc status; command -v claude'
GASCITY_DEMO_CMD='gc status' scripts/gascity-home-container
#+end_src

If =~/.claude/.credentials.json= is missing the script still boots the demo
but prints a warning: =claude= will not be authenticated in the container.

The demo is also available as an opt-in make target.  Like the smoke tests it
is deliberately NOT part of =make check=, as it needs the Guix daemon,
unprivileged user namespaces and the network:

#+begin_src sh
make run-gascity-home-container
#+end_src

** The system-service demo

The =bright-lights= example has a system counterpart,
=examples/gascity/bright-lights-system.scm=, that runs the *machine-wide*
=gascity-service-type= in a fresh, ephemeral system image.  It mirrors
=examples/gascity/system.scm= (one supervisor, the =bright-lights= city, the
builtin =claude= provider, the pinned builtin =core=/=bd= imports) and adds
=claude-code= and the credential install described below.

=scripts/gascity-system-container= wraps the invocation.  By default it builds
and runs a *system container* with =sudo guix system container --network= (the
counterpart of =scripts/gascity-home-container=); pass =--vm= for a rootless
=guix system vm --no-graphic=.

#+begin_src sh
scripts/gascity-system-container          # system container (sudo)
scripts/gascity-system-container --vm     # rootless QEMU VM
#+end_src

A system container needs root to map a 65536-uid/gid range into its user
namespace.  Containers have no =/dev/tty*=, so interact with =guix container
exec= rather than a serial console:

#+begin_src sh
sudo guix container exec "$(cat /tmp/bright-lights.pid)" \
     /run/current-system/profile/bin/bash --login
export GC_HOME=/var/lib/gascity/.gc
cd /var/lib/gascity/bright-lights
gc status                        # supervisor and city status
cd /var/lib/gascity/my-project
gc sling my-project/claude "your task"   # route work to the claude agent
gc session list
#+end_src

The example declares the tutorial's project rig at the service user's
=~/my-project= (=/var/lib/gascity/my-project=, prefix =mp=).  Because the rig
is declared in the city config, the service initializes its beads store
itself, as the =gascity= user, when the city starts, so =gc sling= works
without running =gc rig add=.  Do *not* run =gc rig add= as root: the
container's login shell is root, and root-owned beads files in the rig are
unreadable by the =gascity= supervisor, which then fails city init with
=permission denied= and never starts an agent.  (For an *undeclared* rig,
run =gc rig add <path>= as the =gascity= user, or use =--adopt=.)

With =--vm= the VM presents a serial =login:= prompt: log in as =root= with no
password (a fresh Guix System leaves the root account passwordless) and run
the same =gc= commands.

The city is ephemeral: it lives only in the image and is discarded when it
exits.

** What the VM/container exposes

- The demo never shares the operator's own Claude Code login
(=~/.claude/.credentials.json=, =~/.claude.json=).  The agents run with
=--dangerously-skip-permissions= on untrusted input and can read everything
their user can, so they get a credential of their own.  In *container mode*
the wrapper exposes *read-only* one of:
  - the file named by =GASCITY_CLAUDE_OAUTH_TOKEN_FILE=, holding a token from
    =claude setup-token=, which uses your Claude subscription (preferred);
  - the file named by =GASCITY_ANTHROPIC_API_KEY_FILE=, a Console API key
    created for this city alone, with a spend limit.

  #+begin_src sh
  claude setup-token                 # once, on the host; copy the token
  install -m 600 /dev/stdin ~/.config/gascity-demo-token   # paste it, then C-d
  GASCITY_CLAUDE_OAUTH_TOKEN_FILE=~/.config/gascity-demo-token \
      scripts/gascity-system-container
  #+end_src
- At boot a one-shot Shepherd service, which =user-processes= (and hence the
supervisor) waits for, installs it.  Root only reads the exposed file, then
forks and drops to the =gascity= account, which writes a generated, minimal
=~gascity/.claude.json= (onboarding done plus
=projects[<rig>].hasTrustDialogAccepted= for each declared rig, so =claude=
does not stop at the first-run trust dialog, whose default answer exits a
non-interactive session) and then:
  - for a subscription token, a =CLAUDE_CODE_OAUTH_TOKEN== line in the
    supervisor's =secrets-file= (=/var/lib/gascity/.gc/secrets.env=, =0600=),
    which =gc= forwards to every agent session;
  - for an API key, =~gascity/.claude/anthropic-api-key= (=0600=) and a
    =~gascity/.claude/settings.json= whose =apiKeyHelper= prints it.

  The install cannot run in the activation phase, which precedes every
  file-system mount.
- =guix system vm --expose= exports a *directory* (9p cannot export a single
file), so =scripts/gascity-system-container= stages the credential in a
private temporary directory and exposes that instead; it is removed when the
script exits.  Without either variable the demo boots unauthenticated: run
=claude login= as the =gascity= user.
- The VM uses QEMU's user-mode network (=%qemu-static-networking=), which
=claude= needs.
- On aarch64 the serial console is the PL011 UART (=ttyAMA0=) and the example
also runs its =agetty= there; the script passes QEMU's =-M virt -cpu max=,
without which QEMU's aarch64 emulator has no default machine.  On x86_64 both
the console and the =-M= default are =ttyS0=.

** =--vm=

Passing =--vm= boots a rootless =guix system vm --no-graphic= (QEMU, with KVM
when available) instead of the default container, and forwards the serial
console.  On aarch64 the console is the PL011 UART (=ttyAMA0=) and the example
runs its =agetty= there; the script passes QEMU's =-M virt -cpu max=, without
which QEMU's aarch64 emulator has no default machine.  On x86_64 both the
console and the =-M= default are =ttyS0=.  A system container maps a
65536-uid/gid range into its user namespace, which the kernel permits only for
root (Guix does not use =newuidmap=), hence the =sudo= in the default.  The VM
shares no credentials (QEMU's 9p virtfs hangs on file reads here), so it boots
unauthenticated: run =claude login= inside it, or use the default container.

The VM boots a tiny root image, so the example mounts a 4 GiB tmpfs at the
service state directory (=needed-for-boot?=): Dolt's managed server refuses to
start below its 0.5 GiB free-space floor, which would otherwise fail genesis
for a reason unrelated to the service.  The same tmpfs also caps the
=guix system container= demo, whose state directory would otherwise sit on the
container root: 1 GiB was too small once the bead store and session history
grew, at which point Dolt stopped accepting connections and every agent
stalled.  tmpfs only charges pages that are actually written, so the larger
limit is safe on the VM's 2 GiB of RAM.  The launcher also gives QEMU 2 GiB of
RAM (its 128 MiB default OOM-kills =gc= during genesis).  The system smoke
test (=tests/r0man/guix/services/gascity-container.scm=) carries the same two
workarounds.

The system demo is also available as an opt-in make target.  Like the smoke
tests it is deliberately NOT part of =make check=, as it builds and boots a full
system image and needs the Guix daemon (and QEMU):

* Secrets
  :PROPERTIES:
  :ID:       secrets
  :END:

** The hard policy

*No literal secret may appear anywhere in the Guix configuration.*  Not in a
record, not in the generated =city.toml=/=pack.toml=, not in =files=, and not in
the Shepherd =environment-variables=.  The generated TOML may contain only
=$VAR= / =${VAR}= *references*, which Gas City expands against the supervisor
process environment.

The document builders run =gascity-sanitize-and-validate= on every generated
node list.  It rejects obviously literal secrets (=-sk-ant-...=, =ghp_...=,
long high-entropy tokens, and other known credential shapes) and accepts =$VAR=
references, ordinary paths, =sha:<hex>= pins and =builtin:= names.  A literal
secret in a record is therefore rejected at emission, not silently written.
=gascity-secret-value?= is the underlying predicate.

The =environment-variables= field is for *non-secret* configuration only.

** secrets-file and $GC_HOME/secrets.env

The supervisor configuration's =secrets-file= (accessor
=gascity-supervisor-configuration-secrets-file=) names a dotenv file
(=KEY=VALUE= per line, =#= comments, an optional leading =export=, one layer of
matching quotes) that the service loads into the supervisor environment at
start.  It defaults to =<gc-home>/secrets.env=, matching Gas City's own
convention, and defaults to being materialized mode =0600= and owned by the
service user.  Point it at a decrypted path for sops-guix or any other injection
path.

** The verified gotcha: foreground gc supervisor run does not load secrets.env

Gas City reads =$GC_HOME/secrets.env= only in its *own* service-file generator
(=gc supervisor install= / =gc start=).  The foreground =gc supervisor run= this
service runs under Shepherd *does not* load it.  The service therefore runs the
supervisor through a small wrapper (a =program-file=) that sources the dotenv
=secrets-file= into the environment and then =exec=s
=gc supervisor run=.  Without that wrapper every =$VAR= reference would resolve
empty, a silent provider auth failure.

The wrapper also inherits =GC_SUPERVISOR_ENV= untouched: that is the allowlist
=gc= consults when it forwards non-=GC_= variables to spawned agent sessions, so
a secret reaches agents only when named there.

** sops-guix recipe

[This is a *recipe only*.  The channel ships no =(sops ...)= import and no
companion module: a =(sops ...)= import in the channel's modules would break the
default channel build for users who do not have the extra channel.  The base
service depends on nothing from sops-guix; the generic =secrets-file= also
serves =guix deploy=, a pre-existing =$GC_HOME/secrets.env=, or any other
injection path.]

Add the external channel
(<https://github.com/fishinthecalculator/sops-guix>) to
=~/.config/guix/channels.scm=:

#+begin_src scheme
(cons* (channel
        (name 'sops-guix)
        (url "https://github.com/fishinthecalculator/sops-guix"))
       (channel
        (name 'r0man)
        (url "https://github.com/r0man/guix-channel"))
       %default-channels)
#+end_src

Import the sops module, declare the secret (here the value under the
=gascity/dotenv= key is the whole dotenv blob, written verbatim as a binary),
and wire the decrypted path to =secrets-file=:

#+begin_src scheme
(use-modules (sops services sops))
(use-modules (r0man guix services gascity))

(define gascity-dotenv-secret
  ;; Decrypts the "gascity/dotenv" value of secrets/prod.yaml into a file
  ;; under the sops secrets directory (typically /run/secrets), owned by
  ;; gascity, mode 0400.  The YAML value is the dotenv text itself.
  (sops-secret
   (key '("gascity" "dotenv"))
   (file (local-file "secrets/prod.yaml"))
   (user "gascity")
   (group "gascity")
   (permissions #o400)
   (output-type "binary")))

(operating-system
  ...
  (services
   (append
    (list
     ;; Bring the secret into being at boot (age key derived from the host
     ;; SSH key; see the sops-guix docs for the runbook).
     (service sops-secrets-service-type
              (sops-service-configuration
               (generate-key? #t)
               (host-ssh-key "/etc/ssh/ssh_host_ed25519_key")
               (secrets (list gascity-dotenv-secret))))
     ;; The supervisor loads the decrypted dotenv file on every start.
     (service gascity-service-type
              (gascity-service-config
               (secrets-file (sops-secret->secret-file gascity-dotenv-secret))
               (cities (list (gascity-city-configuration
                              (name "burningswell")))))))
    %base-services)))
#+end_src

=sops-secret->secret-file= returns the decrypted file's path (the sops service
provisions one Shepherd service per secret, named =sops-secret-<key>=), so the
supervisor's wrapper reads exactly what sops wrote.  Encrypted secrets can be
checked into the Guix repository; plaintext never touches disk or the store.

=modify-services= pattern.  When an =operating-system= already carries a sops
service, extend it instead of declaring a second one, and keep the ordering
where sops's one-shot runs before the supervisor.  sops-guix names each secret's
Shepherd service =sops-secret-<key>=, so a service that must wait for one lists
it among its requirements:

#+begin_src scheme
(modify-services %base-services
  (sops-secrets-service-type
   config =>
   (sops-service-configuration
    (inherit config)
    (secrets (cons gascity-dotenv-secret
                   (sops-service-configuration-secrets config))))))
#+end_src

Make the provision one-shot and the supervisor wait for the decrypted file with
the =shepherd-requirement= field (a list of Shepherd service names; the Home
service honours it too):

#+begin_src scheme
(gascity-service-config
 (secrets-file (sops-secret->secret-file gascity-dotenv-secret))
 (shepherd-requirement '(sops-secret-gascity/dotenv))
 ...)
#+end_src

The field is called =shepherd-requirement=, singular, like the
=github-app-token-configuration= field of the same name; the github-actions
services in this channel call theirs =requirements=.  Without it the recipe
still works in practice, because the =respawn? #t= supervisor wrapper re-reads
=secrets-file= on every (re)start, so a first-start race self-heals.

* GitHub identity

Each city commits and opens pull requests as a GitHub identity of its own,
never with the operator's SSH or GPG keys or =gh= login.

The threat model decides the design.  Agents run Claude Code with
=--dangerously-skip-permissions= and read untrusted content (issues, pull
requests, web pages), so assume an agent can run anything as its Unix user
and read every credential that user can.  File modes and environment hygiene
only stop accidental leaks.  The real limits are what GitHub lets the
credential do and how long it lives.  Hence:

- one Unix user (and group) per city: instances that share a user share its
  credentials, and the system service warns about it;
- a Gas City account never joins a privileged group (=wheel=, =sudo=,
  =docker=, =libvirt=, =kvm=, =video=, =input=, =netdev=, =disk=, =root=);
  the service refuses such a =group=;
- short-lived, narrowly scoped tokens, and GitHub-side rules that hold even
  when a token leaks.

** Choosing an identity

| | GitHub App | Machine user |
|-+------------+--------------|
| Identity | =<slug>[bot]= | a second GitHub account |
| Credential | 1-hour installation token, minted by =github-app-token-service-type= | classic personal access token |
| Lifetime | 1 hour, re-minted every 15 minutes when due | up to 90 days, rotated by hand |
| Your own repositories | yes (install the App on them) | yes (as a collaborator) |
| Upstream repositories and forks | no | yes |
| Commit signing | none (see below) | none (see below) |
| Terms of service | unlimited | one free machine account per person |
| =gh= limits | =gh api user=, =@me= queries and =gh repo fork= fail with an installation token | none |

Prefer the App for your own repositories.  Use a machine user for upstream
contributions, which an App cannot make.  Fine-grained tokens do not work for
a collaborator on a personal account's repositories, which is why the machine
user needs a *classic* token.

Both identities hand the consumers the same thing, a token file:

- git reads it through =github-token-credential-helper=, a git credential
  helper that answers only =https://github.com= (any other host, and plain
  =http=, gets nothing) and refuses a token whose =token.expires_at= sidecar
  is in the past;
- =gh= reads it through =github-token-gh=, a wrapper =bin/gh= that sets
  =GH_TOKEN= from the file.  Put it first in the supervisor's =packages=:
  =PATH= is first-wins, and the agents only see =packages=, never a Home
  profile;
- =github-git-config= writes a git configuration with the identity, the
  credential helper, =insteadOf= rewrites from =git@github.com:= and
  =ssh://git@github.com/= to HTTPS (so no SSH key is ever used), and
  =push.autoSetupRemote=.  Pass it as the supervisor's =git-config=: it is
  exported as =GIT_CONFIG_GLOBAL=, a read-only store file the agents cannot
  replace.  =~/.config/git/config= (for example from =guix-home-service-type=)
  is only the fallback for interactive sessions as the user, since the agents
  can rewrite it.

Whatever =git-config= is, =GIT_CONFIG_GLOBAL= names a generated file that first
declares the settings =gc= would otherwise write there and then includes
=git-config=, so a value =git-config= sets wins.  Today that is
=beads.role = maintainer=: =gc='s bundled bd lifecycle script runs =git config
--global beads.role maintainer= at every bead store init when the key is unset,
and fails the init when the write fails, as it does on a read-only store file.
Guix itself ships no git configuration service (only gitolite's), so the file
is the configuration: =github-git-config=, or any =plain-file= or
=mixed-text-file=.

All three live in =(r0man guix services github-token)=, which works from both
system and Home configurations.  The worked examples are
=examples/gascity/github-app.scm= and =examples/gascity/github-machine-user.scm=.

** GitHub App

=github-app-token-service-type= (=(r0man guix services github-app-token)=)
keeps an installation token on disk:

#+begin_src scheme
(github-app-token-configuration
 (name "gascity")                          ; 'github-app-token-gascity
 (client-id "Iv23li...")
 (installation-id 12345678)                ; or (repository "r0man/guix-channel")
 (private-key-file "/run/secrets/gascity-app.pem") ; sops: user github-app-token, 0400
 (reader-group "gascity")                  ; that city's own group only
 (repositories '("guix-channel"))          ; required, non-empty
 (permissions '((contents . "write") (pull_requests . "write")
                (checks . "read") (statuses . "read") (actions . "read")))
 (schedule "*/15 * * * *")                 ; cron string or calendar-event gexp
 (shepherd-requirement '(sops-secret-gascity-app-pem)))
#+end_src

- A dedicated =github-app-token= system account (no login shell, home
  =/var/empty=) is the only reader of the private key.
- The token is written to =/run/github-app-token/<name>/token= (the directory
  is =2750 github-app-token:<reader-group>=), with its expiry in
  =token.expires_at=.  Writes are atomic (temporary file, =fsync=, =rename=).
  Nothing logs the JWT, the token or GitHub's error bodies; the log shows the
  expiry and a short SHA-256 prefix of the token.
- Narrowing is mandatory: =repositories= must be non-empty and =permissions=
  explicit.  =workflows=, =administration=, =secrets=, =environments=, =pages=
  and =actions: write= are refused.
- The one-shot =github-app-token-<name>= mints at boot, retrying for about two
  minutes (a laptop's =networking= comes up before connectivity), and then
  succeeds anyway so the supervisor that requires it still starts.  The timer
  =github-app-token-<name>-refresh= re-mints once the token is less than 30
  minutes from expiry; it does not require the one-shot, and =herd trigger=
  forces a run.  Its output goes to =/var/log/github-app-token.log=.

Require the one-shot from the supervisor with
=(shepherd-requirement '(github-app-token-gascity))=.

Commit as the bot: =user.name= is =<slug>[bot]= and =user.email= is
=<bot-user-id>+<slug>[bot]@users.noreply.github.com=, where the bot user id is
the =id= of =https://api.github.com/users/<slug>%5Bbot%5D=.

Registering the App:

- register it on your own account only, never an organization you don't own;
- turn the webhook off, and leave "Request user authorization (OAuth)" off;
- grant only the repository permissions above;
- install it on *selected* repositories, not "All repositories";
- generate a private key, encrypt it with sops, and delete the download;
- rotate the key by generating a new one, deploying it, then deleting the old
  one on the App's settings page.

** Machine user

- Create the account (one free machine account per person), invite it as a
  collaborator with write access, and keep its email private with "Block
  command line pushes that expose my email" on.  Commit as
  =<id>+<login>@users.noreply.github.com=.
- Create a *classic* token with =public_repo= (or =repo= for private
  repositories) and nothing else.  In particular, no =workflow=.  Set an
  expiry of 90 days or less and calendar the rotation.
- Deliver it with sops-guix as a file readable only by the city's user
  (=0400=), and list the secret's Shepherd service in the supervisor's
  =shepherd-requirement=.

** Commit signing

Agent commits are not signed.  A signing key the agent can read proves
nothing about who wrote the commit, and the "Verified" badge would suggest
otherwise.  For a "Verified" history on =main=, squash-merge pull requests in
the web UI: GitHub signs the merge commit itself.

** File versus environment

The token is a file, not an environment variable, so it does not end up in
every child's environment, in =/proc/<pid>/environ= dumps or in logs that
print the environment.  This is hygiene, not a boundary: the agent can read
the file.  A later phase could put a credential broker, running as a separate
user, between the agents and GitHub that adds the =Authorization= header
itself, so the agents never hold a token at all.

** Mandatory GitHub-side guardrails

These rules are what contains a leaked or misused token.  Set them up before
the first agent push:

- a ruleset on =main= and on tags: pull request required, review from code
  owners (a =CODEOWNERS= naming =@r0man=), approval of the most recent push,
  stale approvals dismissed, no force pushes, no deletion, and the bot never
  on the bypass list;
- a ruleset limiting the bot's branches to =gascity/**=;
- the default =GITHUB_TOKEN= permissions set to read-only;
- no =pull_request_target= or =workflow_run= workflow that checks out a pull
  request's head;
- self-hosted runners and jobs that use secrets gated behind an environment
  with a required reviewer.  This matters here: this channel's workflows run
  on =[self-hosted, docker]=;
- secret-scanning push protection on;
- vigilant mode on the operator's account, so unsigned commits claiming to be
  the operator show as "Unverified";
- rulesets on private repositories of a personal account need GitHub Pro.

** Host hardening

Outside this channel, in the operator's own system configuration:

- =DenyUsers gascity*= in =sshd_config=, so an agent cannot plant an
  =authorized_keys= and log in;
- =kernel.yama.ptrace_scope=1=;
- =umask 077= for the operator, so the agents cannot read the operator's new
  files;
- nftables egress rules per Gas City user (=meta skuid=): block =127.0.0.0/8=
  except the city's own ports, the LAN and Tor's =9050=, optionally sending
  everything else through an allowlisting proxy;
- the supervisor's =read-auth= and =write-auth= settings enabled for every
  city, so another local user cannot drive its API.

** Claude Code credentials

Never copy the operator's =~/.claude/.credentials.json= or =~/.claude.json=
into a service user's home: that hands the agents your interactive login,
refresh token included.  Give each city a credential of its own instead:

- *Subscription (preferred for personal cities).*  Run =claude setup-token=
  once and put =CLAUDE_CODE_OAUTH_TOKEN=<token>= in the city's
  =secrets-file= (through sops-guix in a real system).  The supervisor loads
  it into its environment, and =gc= passes =CLAUDE_CODE_OAUTH_TOKEN= on to
  every agent session by itself; no =GC_SUPERVISOR_ENV= entry is needed.  It
  costs nothing extra, but has no spend limit: the agents draw on the same
  rate limits as your own Claude Code use.
- *Console API key.*  Billed per token, with a hard spend limit per key.
  Deliver it the same way as =ANTHROPIC_API_KEY=, or through an
  =apiKeyHelper= in the service user's =~/.claude/settings.json=.

Either way, generate a minimal =~/.claude.json= with only the onboarding flag
and the trust entries of the city's rigs.
=examples/gascity/bright-lights-system.scm= does both.

** Revocation runbook

When a city misbehaves or a credential may have leaked:

1. Suspend the App's installation (Settings → Applications → Configure →
   Suspend), or remove the machine user's collaborator access.
2. Delete the App's private key on its settings page.
3. Stop the city: =herd stop gascity-supervisor= (or the instance's
   suffixed name), then kill its tmux sessions (=pkill -u gascity tmux=).
4. Revoke the machine user's token and the city's Claude credential (the
   =setup-token= token or the Console API key).
5. Keep the state directory as it is, for forensics.

* Lifecycle and ownership

The loop runs per supervisor instance; =GC_HOME= is the instance's =gc-home= and
every derived path is keyed off it.  Two phases:

- Activation (root for system, the user for home) materializes *declarative
  files* only: it creates the state, log and =gc-home= directories, writes each
  enabled city's =.gc/site.toml= and then its generated =city.toml= and
  =pack.toml= (unchanged files are left alone, so a no-op reconfigure does not
  perturb a running controller),
  converges =files=/=rig-files= (see [[*files and rig-files]]), and writes each
  instance's =supervisor.toml= (=0600=).  It runs =gc= only for a city that
  is already running and whose files it changed: =gc import check=/=install=
  for =install-packs?= and =gc reload --soft= for =soft-reload?= (see
  [[*Reload and restart]]); it never runs =gc init=.

  For the system service, root never writes below the state directory.  The
  agents run as the service user and can plant symbolic links anywhere it owns
  (=ln -s /etc ~/.gc=), and every file operation of a root process follows
  them.  So root only:

  - creates the state directory (=0700=, the service user's) and the log
    directory (=0750=, =root:<group>=), refusing a symbolic link and any
    ancestor that is not a root-owned, non-writable directory, and changing
    ownership through an =O_NOFOLLOW= descriptor;
  - removes anything but a plain file at the supervisor and provision log
    paths, and pre-creates the provision log (=0640=, the service user's);
  - then forks, drops its supplementary groups, =setgid=/=setuid=s to the
    service account, and writes everything else as that user.

  The log directory stays root's because Shepherd opens the supervisor's
  =#:log-file= as root and follows symbolic links.  An instance whose
  activation refuses a path or fails is reported and skipped; it does not
  abort the activation of the rest of the system.  The Home service runs as
  the user already and writes everything in-process.
- Provision one-shot (runs as the service user, and the supervisor =requires=
  it) does the *stateful* work per instance: writes =.gc/site.toml=, runs
  =gc init --file <city>/city.toml --preserve-existing --no-start
  --skip-provider-readiness= for each city (=genesis?=), optionally runs =gc
  import install --city <city>= (=install-packs?=), then read-merge-writes the
  =cities.toml= registry (=register?=).  On every run, stamp or not, it then
  re-syncs the imports of each =install-packs?= city (see
  [[*Imports and packs.lock]]).  It performs no network access unless a city
  opts into =install-packs?=.  The program is *re-runnable*: a stamp under
  =GC_HOME= short-circuits a rerun whose generated inputs are unchanged, so a
  supervisor stop/start or =herd restart= within one boot does not re-run
  genesis (see below).

Then Shepherd starts the secrets-loading wrapper that =exec=s =gc supervisor
run= as the service user, using the instance's =gc-home=, =XDG_RUNTIME_DIR= and
=port=.

Both the one-shot and the supervisor (and so every agent) also get:

- =TMPDIR= pointing at =<state-directory>/tmp= (=0700=, created by the
  one-shot), so agent temporary files never land in the shared =/tmp=;
- =GIT_TERMINAL_PROMPT=0=, so a git that wants a password fails instead of
  hanging a session;
- =SSL_CERT_FILE=, =SSL_CERT_DIR= and =GIT_SSL_CAINFO=: the values Shepherd
  itself runs with, otherwise =/etc/ssl/certs= when it exists;
- =GIT_CONFIG_GLOBAL= when =git-config= is set.

** Re-runnable gc init --preserve-existing

Genesis is =gc init ... --preserve-existing --no-start
--skip-provider-readiness= (=genesis?=).  That command is *not* idempotent in
current =gc= releases: a second run refuses with =gc init: already initialized=
(exit code 2).  Shepherd also forgets that a one-shot service already ran once
it exits, so every start of a dependent supervisor re-runs the provision
program.  The service therefore makes the rerun safe:

- it keeps a stamp of the generated inputs of the last successful run (the
generated =city.toml=/=pack.toml=, the =.gc/site.toml= text this program
writes, the =genesis?=/=install-packs?=/=register?= flags and the =gc=
package) in =<gc-home>/.gascity-provision-stamp=;
- a rerun whose inputs still match, and whose city scaffolds and registry
still exist, short-circuits with exit 0 — so a supervisor stop/start or =herd
restart= inside one boot does not re-run genesis;
- a change to any of them — including a reconfigure that changes the generated
files or flags — yields a different stamp and provisions again;
- =gc init= exit code 2 is also accepted as success, so a system provisioned
by an earlier generation (which has no stamp yet) upgrades without a spurious
failure.

The generated =city.toml= and =pack.toml= must exist on disk *before* genesis,
which is why the activation runs first.

** cities.toml ownership

The registry holds =[[cities]]=, =[[rigs]]= and =[[pending_city_requests]]= in
one file, and =gc= rewrites it under an =flock=.  The service writes it with a
locked read-merge-write that replaces exactly the declared and enabled
=[[cities]]= set and preserves everything else verbatim:

| Owned by this service | Owned by =gc= |
|-----------------------+--------------|
| the declared + enabled =[[cities]]= set (path and name) | =[[rigs]]= |
| | =pending_city_requests= |
| | any other section the operator or =gc= adds |

The service deliberately does *not* call =gc register=: on non-systemd-delegated
systems =gc register= regenerates and installs =gc='s own service unit and
starts a supervisor, fighting Shepherd.  A manual =gc register= (or =gc rig
add=) in a service-managed =GC_HOME= is *overwritten* and unsupported — the
declared set is authoritative for =[[cities]]=.

** Removing or disabling a city

The declared-and-enabled set is exactly =[[cities]]=.  Setting =(enabled? #f)=
or removing a city from the list unregisters it (the read-merge-write drops it
and the supervisor reload applies the change) while preserving =[[rigs]]= and
=pending_city_requests=.  Generated files, =.gc/= and =.beads/= are *never*
deleted on disk.  Re-enabling or re-adding a city re-registers it.

** genesis? / install-packs? / register? semantics

| Field | Default | Meaning |
|-------+---------+---------|
| =genesis?= | =#t= | run the idempotent =gc init ... --preserve-existing= for the city |
| =install-packs?= | =#f= | keep the city's installed imports in step with its declaration: =gc import check=, then =gc import install= on drift (see [[*Imports and packs.lock]]) |
| =register?= | =#t= | include the city in the declared =[[cities]]= set of the instance's registry |
| =soft-reload?= | =#t= | after an activation changed the city's files, ask its controller for =gc reload --soft= (see [[*Reload and restart]]) |

A city with =register? #f= is materialized and genesis-ed but never registered
(useful for a city another supervisor owns).  =install-packs? #t= makes the
supervisor wait on a network fetch; a fetch failure leaves the city visibly down
without failing the system reconfigure.

** Per-instance port rules

Gas City cannot disable its API listener (=[supervisor].port <= 0= resolves to
8372, and a failed bind exits with a port-in-use code, which under Shepherd
would crash-loop).  A lone instance defaults to =8372=; every instance of a
multi-instance value must set =port= explicitly, and two instances that share a
=(bind, port)= — or a =gc-home= — fail closed at evaluation.  Never persist an
ephemeral port.  The service forwards =[supervisor].port= into the generated
=supervisor.toml=.

** Rigs

A rig needs no =gc rig add=.  Declare it in the city's =rigs= with its =path=:
the path goes to =.gc/site.toml= (schema 2) and the rest to =city.toml=.  Each
time a city controller starts the city or applies a changed configuration, it
initializes the beads store of every rig =.gc/site.toml= gives a path, and
keeps an existing store: a checkout whose =.beads/= already carries the rig's
=prefix= is adopted as it is, so its bead IDs survive.  =gc init= itself never
touches rigs.

The activation writes =.gc/site.toml= *before* =city.toml=.  The controller
does not reload for a change to =.gc/site.toml= alone (its watcher ignores
=.gc/=, and the file is not part of the config revision), so a reload that the
new =city.toml= triggers must already find the new rig's path; otherwise it
would skip the rig until the next restart.  For the same reason, changing only
an existing rig's =path= takes effect at the next =herd restart= of the
supervisor.

** Imports and packs.lock

A city loads a remote import only when =packs.lock= in its root has an entry
for it and the pinned checkout is in the cache under =GC_HOME=; otherwise the
city fails to load and keeps its previous configuration.  =gc init= installs
the imports of a new city.  For an existing city, =install-packs? #t= keeps
them in step with the declaration:

- the activation, for a running city whose files it changed (a new =version=
  pin in =pack.toml=, for example), and
- the provision one-shot, on every run,

run =gc import check --city <city>= (offline) and, only when it reports drift,
=gc import install --city <city>=.  A failed install is logged and never fails
the activation or the provision: the other cities keep running and the next
activation or supervisor start retries.  With =install-packs? #f= the imports
are left to =gc= (the bundled packs at the binary's own pins need no install).

** Reload and restart

The activation writes =city.toml=, =pack.toml=, =.gc/site.toml= and the
=files= of each city, and when any of them changed in a city that is running,
it runs =gc reload --soft --async <city>= (=soft-reload?=, on by default).  The
controller's own file watcher would reload a changed =city.toml= too, but as a
plain reload: every open session whose configuration changed is then drained
and restarted, including the agent session that may be driving this very
reconfigure.  A soft reload accepts that drift instead, and cancels drains the
watcher already began, so open sessions keep running and pick the new
configuration up when they next start.  With =soft-reload? #f= the service
leaves the change to the watcher, and drifted sessions are drained.

The supervisor itself is reloaded (=gc supervisor reload=) only when the
registry or supervisor settings changed; a =port=/=bind= change restarts it
instead.  All of this is non-fatal, and none of it touches the network unless
=install-packs?= asks for an import install.

* Migrating from burningswell

The existing =burningswell= provisioning in =~/common-lisp/burningswell-cl/.guix=
converges a live city with awk helpers (=converge_kv=, =converge_block=,
=converge_file=) that re-assert declared =city.toml= keys and block regions on
every activation, reloading the controller only when something really changed.

*** This migration is a separate, user-owned change (not performed here)

The actual =burningswell= migration is a *separate, user-owned change outside
this repository*, and was *not* performed by this manual.  It is not part of the
channel and nothing in the channel reads or edits the =burningswell= =/.guix=
tree.  The mapping below is guidance for that future change.

How the awk-converging activation maps onto this service:

| burningswell idiom | Gas City service |
|--------------------+------------------|
| SCAFFOLD phase (stamp-guarded: =gc init=, =gc import install=, =gc rig add=, =gc register=) | the provision one-shot: =gc init --preserve-existing= (=genesis?=) and the locked =[[cities]]= read-merge-write (=register?=), stamp-guarded under =GC_HOME=; rigs need no =gc rig add= (see [[*Rigs]]) |
| =gc import check= / =gc import install= on drift | =install-packs? #t=: the activation and the provision re-sync on drift, non-fatally |
| =converge_rig_checks= (pack check scripts copied into the rig, helpers symlinked) | =rig-files= with a directory source and =gascity-symlink= entries |
| a writable =~/.gitconfig= for =beads.role= | the generated =GIT_CONFIG_GLOBAL= declares =beads.role=; the git configuration stays read-only |
| CONVERGE phase (=converge_kv= restates declared =city.toml= keys every activation) | the declarative generator: activation writes whole generated =city.toml=/=pack.toml= only when they differ; the record is the source of truth |
| =converge_block=/=converge_tree= fenced regions and whole files | =files= / =rig-files= and the typed records; whole files, no fenced markers |
| whole generated files | =city.toml= from the city record, =pack.toml= from the city's =pack= field |
| the list of cities and rigs | the supervisor's =cities= list and each city's =rigs= |
| derived paths (=~/burningswell=, =%gascity-github-token-path=) | =directory=, =gc-home=, =state-directory=, =log-directory=, and =secrets-file= |
| =gc reload --soft= when a key changed | =soft-reload? #t= (the default): the activation runs =gc reload --soft --async= for a running city whose files it changed |
| the city is provisioned by a Home activation | the derived =home-gascity-service-type=, or the system service |

The two-phase split is the same insight: creation and machine-local
registration are one-shot, declarative content is converged every activation.
The service replaces the hand-rolled convergence with generated whole files and
the idempotent =gc init --preserve-existing=.
