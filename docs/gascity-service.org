#+title: The Gas City service
#+options: toc:2

This manual documents the Gas City service shipped by the =r0man= Guix
channel: the system service =gascity-service-type=, the derived home service
=home-gascity-service-type=, and the Guix record surface that compiles to Gas
City's =city.toml=, =pack.toml= and =supervisor.toml=.  Gas City itself is
documented at <https://github.com/gastownhall/gascity>.

The service layers:

- =gascity-service-type= (=r0man guix services gascity=) — runs one or more
  machine-wide Gas City supervisors (=gc supervisor run=) as daemons, each in
  its own =GC_HOME=.
- =home-gascity-service-type= (=r0man guix home services gascity=) — the user
  counterpart, running supervisors under =$HOME/.gc= as the user who owns the
  Home environment.  It re-exports every record and accessor of the system
  module, so a Home configuration needs only the home module import.
- =r0man guix toml= — the TOML intermediate representation and emitter the
  serializers build on, and the constructors the =extra-config= escape hatch
  uses.
- =r0man guix services gascity records= — the *generated* leaf-record surface,
  produced from the committed Gas City JSON schemas.  See [[#generated-records]].

* Overview

** The service value is a list of supervisors

The value of =gascity-service-type= is a =list= of
=<gascity-supervisor-configuration>= records, one per supervisor process (the
same shape as =github-actions-runner-service-type=).  A single-element list is
the common case; =gascity-service-config= builds it for you:

#+begin_src scheme
(service gascity-service-type
         (gascity-service-config
          (cities (list (gascity-city-configuration
                         (name "swarm"))))))
#+end_src

Pass a plain =list= when you want more than one supervisor.  Each record may
also carry a list of cities; =gascity-service-config= is just sugar for a
one-element list.

** GC_HOME isolation

Gas City isolates supervisors by =GC_HOME=: the registry (=cities.toml=), the
settings (=supervisor.toml=), the control socket, the instance lock and the
runtime/events state all live under it.  The service pins =GC_HOME= *and*
=XDG_RUNTIME_DIR= to each instance's =gc-home=, so an isolated supervisor never
touches the host supervisor's socket or lock.

| Concern | Path | Isolated by |
|---------+------+-------------|
| city registry | =$GC_HOME/cities.toml= | =gc-home= |
| supervisor settings | =$GC_HOME/supervisor.toml= | =gc-home= |
| control socket / lock | =$GC_HOME/supervisor.{sock,lock}= | =gc-home= |
| API listener | =bind=:=port= | =port= (must be distinct) |
| per-city tmux server | =tmux -L <city-name>= | city name / =[session].socket= |
| per-city Dolt | port hashed from the city path | city path |

Two instances that share a =gc-home= or a =(bind, port)= fail closed at
evaluation.  A lone instance defaults to port =8372=; every instance of a
multi-instance service must set =port= explicitly.  A system supervisor and a
home supervisor on the same host share the network namespace, so they too need
distinct ports.

** Dolt author identity
:PROPERTIES:
:CUSTOM_ID: dolt-identity
:END:

=gc init= of a managed bd store runs Dolt's =init=, which commits a bootstrap
revision and therefore needs a commit author identity.  Dolt reads it from
=$DOLT_ROOT_PATH/.dolt/config_global.json= (or =$HOME/.dolt=) and fails at
genesis when it is absent, so the provision one-shot fails and the supervisor
never starts.  The root activation (not the one-shot) materializes
=<state-directory>/.dolt/config_global.json= (=0600=, owned by the service
user):

| Field | Default |
|-------+---------|
| =dolt-user-name= | =Gas City= |
| =dolt-user-email= | =gascity@localhost= |

- Setting *either* field is explicit intent: the file is rewritten, the unset
  field filled with the default above.
- When *both* are unset the default identity is written only if no file exists
  yet; an existing file (an operator- or sops-provided identity) is left
  untouched, so the service never clobbers it.
- The write is compare-and-write, so an unchanged reconfigure does not touch
  the file.

The service user's home is the state directory, so =$HOME= and
=$DOLT_ROOT_PATH= both point at it; the provision one-shot and the supervisor
environment pin =DOLT_ROOT_PATH= explicitly.  This is service configuration,
not a Gas City TOML key: it is never emitted into =city.toml= or
=supervisor.toml=.

** Multiple cities

One supervisor manages a list of cities.  Each city owns a directory, its
generated =city.toml=/=pack.toml=, its =files=, and its registration in the
instance's =cities.toml=.  City names must be unique per supervisor (they become
the tmux socket names); distinct supervisors may manage disjoint or disjointly
named cities.

#+begin_src scheme
(service gascity-service-type
         (gascity-service-config
          (cities (list (gascity-city-configuration
                         (name "burningswell")
                         (directory "/var/lib/gascity/burningswell"))
                        (gascity-city-configuration
                         (name "sandbox")
                         (directory "/var/lib/gascity/sandbox"))))))
#+end_src

* Gas City docs -> Guix records

Every record's accessor is named =gascity-<record>-<field>=, and the field is
the TOML key with =_= replaced by =-=.  Declaration order in the record is
emission order in the generated TOML.

** Field-type conventions

| Convention | Scheme type | Emission |
|------------+-------------+----------|
| optional scalar | ='unset= | nothing |
| optional string | string or ='unset= | =key = "value"= |
| maybe-string-or-gexp | string, gexp or ='unset= | =key = "..."=, gexp spliced verbatim between the quotes |
| tri-state boolean | ='unset=, =#t= or =#f= | nothing, =true= or =false= |
| maybe boolean | ='unset=, =#t= or =#f= | nothing, =true= or =false= |
| integer / real | exact / inexact number or ='unset= | decimal |
| list of strings | Scheme list, default ='()= | =key = ["a", "b"]= |
| string map | alist ='(("K" . "v") ...)= | =key = { K = "v", ... }= |

- ='unset= is the absent marker; an absent field emits nothing, so Gas City
  applies its own default.  This is what makes tri-state booleans and
  presence-aware patches work.
- Predicates =gascity-tri-state?=, =gascity-maybe-string?= and
  =gascity-maybe-string-or-gexp?= test these shapes.
- Strings that may embed a store path (commands, scripts) are typed
  =maybe-string-or-gexp=: a gexp is a first-class TOML value kind and is spliced
  verbatim between the surrounding quotes.  Only literal fragments are escaped
  at build time; a spliced gexp must not need further escaping.
- Array tables that Gas City spells in the singular (=[[agent]]=,
  =[[named_session]]=, =[[rigs]]=) get a *plural* record field (=agents=,
  =named-sessions=, =rigs=); the TOML key is unchanged.
- Maps keyed by a name (=providers=, =upstreams=, =imports=, and the pack's
  =runtimes=) are alists of =(name . record)=, e.g.
  =(providers (list (cons "claude" (gascity-provider-configuration ...))))=.

** The generated leaf records

Every documented field of Gas City's =City= and =Pack= schemas is mirrored by a
*generated* leaf record in =modules/r0man/guix/services/gascity/records.scm=,
module =(r0man guix services gascity records)=.  That file is generated from the
committed schemas =docs/reference/schema/{city,pack}-schema.json= by
=scripts/generate-gascity-records.scm=; regenerate it with =make
generate-gascity-records= and check it with =make check-gascity-records=.  Do
not edit it by hand.

The generated records follow the same conventions: the module is
=(r0man guix services gascity records)=, each record is
=<gascity-<name>-configuration>= with =gascity-<name>-configuration-<field>=
accessors, every field defaults to ='unset=, and the leaf records whose
hand-written sibling lives in =gascity.scm= exist in both (the hand-written one
is the Phase-2 subset the service itself needs).  When you need a field the
hand-written records do not expose, import the generated module, or reach the
key through =extra-config=.

* Worked examples

All examples below are the shapes the test suite renders verbatim
(=tests/r0man/guix/services/gascity.scm=), so they are known to match the
implemented API.

** City: the swarm example

Gas City docs:

#+begin_src toml
[workspace]
name = "swarm"
provider = "claude"

[providers.claude]
base = "builtin:claude"

[daemon]
patrol_interval = "30s"
max_restarts = 5
restart_window = "1h"
shutdown_timeout = "5s"

[[rigs]]
name = "checkout-service"
prefix = "cs"
formula_vars = { push = "true", open_pr = "true", drain_policy = "separate" }
#+end_src

Guix records:

#+begin_src scheme
(gascity-city-configuration
 (name "swarm")
 (directory "/var/lib/gascity/swarm")
 (workspace (gascity-workspace-configuration
             (name "swarm")
             (provider "claude")))
 (providers
  (list (cons "claude"
              (gascity-provider-configuration (base "builtin:claude")))))
 (daemon (gascity-daemon-configuration
          (patrol-interval "30s")
          (max-restarts 5)
          (restart-window "1h")
          (shutdown-timeout "5s")))
 (rigs (list (gascity-rig-configuration
              (name "checkout-service")
              (prefix "cs")
              (formula-vars '(("push" . "true")
                              ("open_pr" . "true")
                              ("drain_policy" . "separate")))))))
#+end_src

** extra-config (structured escape hatch)

=extra-config= is a list of TOML IR nodes layered over the generated document
*before* emission: a field at the same full TOML key *replaces* the generated
field, and a table *merges recursively*.  A key declared twice inside
=extra-config= at one level is an error.  Build the nodes with the
=(r0man guix toml)= constructors =toml-table=, =toml-field=,
=toml-array-of-tables=, =toml-inline-table= and =toml-array=; keys may be
symbols or strings.

#+begin_src scheme
(gascity-city-configuration
 (name "experiment")
 (extra-config
  (list (toml-table 'experimental
                    (toml-field 'feature_flag "true")))))
;; => [experimental]
;;    feature_flag = "true"
#+end_src

Overriding a generated field:

#+begin_src scheme
(gascity-city-configuration
 (name "m")
 (workspace (gascity-workspace-configuration
             (name "a")
             (provider "claude")))
 (extra-config (list (toml-table "workspace" (toml-field "name" "b")))))
;; => [workspace]
;;    name = "b"
;;    provider = "claude"
#+end_src

** extra-toml (raw append)

=extra-toml= is a string or a =file-like= appended verbatim at the end of the
generated file.  It can only add whole new tables: a verbatim append cannot add
a root-level scalar after a table header, nor extend a table the generator
already emitted (that would be a duplicate-table error).

#+begin_src scheme
(gascity-city-configuration
 (name "t")
 (workspace (gascity-workspace-configuration (name "t")))
 (extra-toml "[extra_table]\nk = 1\n"))
#+end_src

** files and rig-files

=files= is a list of =(destination . file-like)= pairs copied into the city
root; =rig-files= into each declared rig root.  Both are data only: they are
never emitted to TOML.  This is how prompt templates, formulas, orders, skills,
=.mcp.json=, scripts and overlays are supplied.

#+begin_src scheme
(gascity-city-configuration
 (name "burningswell")
 (files (list (cons "prompts/mayor.md" (plain-file "mayor.md" "You are the mayor."))
              (cons ".mcp.json" (local-file "city/.mcp.json"))))
 (rig-files (list (cons "scripts/gate.sh" (local-file "gates/gate.sh")))))
#+end_src

Destinations are relative to the root and may not escape it; executable bits
are preserved.

* Running the examples

The channel ships two runnable example configurations, one per service, each
running a single supervisor with one trivial =swarm= city.  Both use the
service defaults, so neither hardcodes the host's =$HOME= or a state path.

- =examples/gascity/home.scm= — a =home-environment= using
  =home-gascity-service-type=.  Build it, or run its activation and a command
  in a container:

  #+begin_src sh
  guix home build -L modules examples/gascity/home.scm
  guix home container -L modules examples/gascity/home.scm -- gc --version
  #+end_src

  The state and log directories default to =$XDG_STATE_HOME/gascity= and
  =GC_HOME= to =$HOME/.gc=.

- =examples/gascity/system.scm= — an =operating-system= using
  =gascity-service-type=, in the style of =simple-operating-system=.  Build a
  VM or a container:

  #+begin_src sh
  guix system build -L modules examples/gascity/system.scm
  guix system vm -L modules examples/gascity/system.scm
  guix system container -L modules examples/gascity/system.scm
  #+end_src

  The supervisor runs as the =gascity= account, with state under
  =/var/lib/gascity=.  The serial console is architecture-dependent: the
  example selects =ttyAMA0= on aarch64 (where QEMU's =virt= machine wires its
  PL011 UART), so on aarch64 the generated =guix system vm= launcher needs
  QEMU's machine and CPU, =$(guix system vm -L modules examples/gascity/system.scm)
  -M virt -cpu max=, while on x86_64 =guix system vm -L modules
  examples/gascity/system.scm= works as-is.

=scripts/gascity-container-smoke-test= wraps the image invocations:

#+begin_src sh
scripts/gascity-container-smoke-test home     # Home activation and generated TOML
scripts/gascity-container-smoke-test system   # machine-wide lifecycle
scripts/gascity-container-smoke-test all      # both, in that order
#+end_src

The =home= check builds =examples/gascity/home.scm= with
=guix home container=, runs the Home activation, and asserts in the container
that the state directory and the generated =city.toml=, =pack.toml= and
=supervisor.toml= exist and contain the expected keys, then runs
=gc config show --validate= in the generated city directory (skipping
gracefully if =gc= is unavailable).  It prints =PASS= or =FAIL: reason= and
exits non-zero on failure.  Because =guix home container= never starts
=home-shepherd-service-type=, the provision one-shot (genesis, site binding,
registry) and the running user shepherd are not covered here; the unit tests
cover them, and the =system= check covers the machine-wide path.

The =system= check builds =tests/r0man/guix/services/gascity-container.scm=, a
test-only =operating-system= that mirrors =examples/gascity/system.scm= and adds
a one-shot assertion service.  It boots the OS's real shepherd (PID 1), so the
full machine-wide lifecycle runs: activation materializes =city.toml= and
=pack.toml=, the provision one-shot runs genesis and registers the city, and
=gc supervisor run= is running as the =gascity= account.  The assertion service
waits (bounded) for =supervisor.sock= and =cities.toml=, then checks that
=city.toml=, =pack.toml=, the =.gc/site.toml= site binding and the =cities.toml=
registry exist, that the =gascity-supervisor= service is running, that the
state is owned by the =gascity= account, and finally that
=gc config show --validate= accepts the generated city.  It writes =PASS= or
=FAIL: reason= into a host directory shared with =--share=, and the script maps
that to =PASS: system= or a non-zero exit.  The image never shuts down by
itself: the script polls the shared directory for the verdict under a hard
timeout, then tears the image down and kills its process group.

The =system= check prefers =guix system container=, which boots the shepherd
without emulation.  That path requires mapping a 65536-uid/gid range into the
container's user namespace, which the kernel permits only for root (Guix does
not use =newuidmap=); on an unprivileged host the container exits at once with
=EPERM=, so the script falls back to =guix system vm --no-graphic=.  The VM
boots the very same OS with the same assertions and needs no privileges (QEMU
is used, with KVM when available).  The =system= section of
=tests/r0man/guix/services/gascity-container.scm= documents that fallback.

The checks are also available as opt-in make targets.  They are deliberately
NOT part of =make check=, as they need the Guix daemon and, for the VM
fallback, QEMU:

#+begin_src sh
make check-gascity-home-container     # scripts/gascity-container-smoke-test home
make check-gascity-system-container   # scripts/gascity-container-smoke-test system
make check-gascity-containers         # scripts/gascity-container-smoke-test all
#+end_src

* Interactive container demo

The =bright-lights= example,
=examples/gascity/bright-lights-home.scm=, is a runnable Home environment for
the [[https://github.com/gastownhall/gascity][Gas City]] quickstart: one
supervisor running a fresh city called =bright-lights= with the builtin
=claude= provider.  It puts =claude-code= on both the supervisor's agent
=PATH= (so =gc sling= can spawn a claude agent) and the interactive user's
=PATH=, and shares the host Claude Code state so an existing login keeps
working inside the container.

=scripts/gascity-home-container= wraps the invocation.  It builds and runs the
example with =guix home container=, waits (bounded) for
=home-gascity-supervisor= to reach =Started=, prints a short banner and drops
you into a login shell:

#+begin_src sh
scripts/gascity-home-container
#+end_src

The banner tells you the city directory and =GC_HOME=, and the two commands
that matter inside the shell:

#+begin_src sh
gc status                        # supervisor and city status
gc sling claude "your task"      # route work to the claude agent
#+end_src

The demo registers an ephemeral =bright-lights= rig in the container
(=~ /bright-lights-rig=) so =gc sling claude ...= has a target out of the box;
this is best-effort and a failure is not fatal.  Before slinging, =cd= into
the rig (=cd ~/bright-lights-rig=).  It does not call the Anthropic API itself.

** What the container shares

- =$HOME/.claude= and, when present, =$HOME/.claude.json= are mounted
  *read-write* (=--share=), so the container reuses the host's Claude Code
  credentials.  Only Claude Code itself writes there.  *The container is
trusted and local:* it can read and write your Claude Code state, so run it
  only on your own machine.
- The host =/bin= is exposed (=--expose=/bin=/bin=).  =guix home container=
  provides no =/bin= at all, but the generated bead shim (=gc-beads-bd.sh=) is
  =#!/bin/sh= and the login shell is =bash=; without it the provision one-shot
  cannot start Dolt and the supervisor never comes up.
- The container accesses the *network* (=--network=), which =claude= needs.

** The city is ephemeral

The state directory is pinned to =$HOME/.local/state/gascity=, =GC_HOME= to
=$HOME/.gc=, and =guix home container= mounts a volatile tmpfs over =$HOME=.
The whole city therefore lives inside the container and is discarded when you
exit: nothing is written to the host home except what Claude Code itself
writes under the shared =~/.claude=.

The demo also shares the host *network namespace* (required for =claude=),
and a machine-wide supervisor already owns the default API port =8372=, so the
example binds =18372= instead.  Override it with =GASCITY_DEMO_PORT= when the
host already uses that port.

** Non-interactive use

A command after =--= runs in the container instead of the login shell (still
after the wait) and its exit status is propagated; =GASCITY_DEMO_CMD= does the
same with a single command line.  Both are what the non-interactive checks
use:

#+begin_src sh
scripts/gascity-home-container -- gc status
scripts/gascity-home-container -- sh -c 'gc status; command -v claude'
GASCITY_DEMO_CMD='gc status' scripts/gascity-home-container
#+end_src

If =~/.claude/.credentials.json= is missing the script still boots the demo
but prints a warning: =claude= will not be authenticated in the container.

The demo is also available as an opt-in make target.  Like the smoke tests it
is deliberately NOT part of =make check=, as it needs the Guix daemon,
unprivileged user namespaces and the network:

#+begin_src sh
make run-gascity-home-container
#+end_src

* Secrets
  :PROPERTIES:
  :ID:       secrets
  :END:

** The hard policy

*No literal secret may appear anywhere in the Guix configuration.*  Not in a
record, not in the generated =city.toml=/=pack.toml=, not in =files=, and not in
the Shepherd =environment-variables=.  The generated TOML may contain only
=$VAR= / =${VAR}= *references*, which Gas City expands against the supervisor
process environment.

The document builders run =gascity-sanitize-and-validate= on every generated
node list.  It rejects obviously literal secrets (=-sk-ant-...=, =ghp_...=,
long high-entropy tokens, and other known credential shapes) and accepts =$VAR=
references, ordinary paths, =sha:<hex>= pins and =builtin:= names.  A literal
secret in a record is therefore rejected at emission, not silently written.
=gascity-secret-value?= is the underlying predicate.

The =environment-variables= field is for *non-secret* configuration only.

** secrets-file and $GC_HOME/secrets.env

The supervisor configuration's =secrets-file= (accessor
=gascity-supervisor-configuration-secrets-file=) names a dotenv file
(=KEY=VALUE= per line, =#= comments, an optional leading =export=, one layer of
matching quotes) that the service loads into the supervisor environment at
start.  It defaults to =<gc-home>/secrets.env=, matching Gas City's own
convention, and defaults to being materialized mode =0600= and owned by the
service user.  Point it at a decrypted path for sops-guix or any other injection
path.

** The verified gotcha: foreground gc supervisor run does not load secrets.env

Gas City reads =$GC_HOME/secrets.env= only in its *own* service-file generator
(=gc supervisor install= / =gc start=).  The foreground =gc supervisor run= this
service runs under Shepherd *does not* load it.  The service therefore runs the
supervisor through a small wrapper (a =program-file=) that sources the dotenv
=secrets-file= into the environment and then =exec=s
=gc supervisor run=.  Without that wrapper every =$VAR= reference would resolve
empty, a silent provider auth failure.

The wrapper also inherits =GC_SUPERVISOR_ENV= untouched: that is the allowlist
=gc= consults when it forwards non-=GC_= variables to spawned agent sessions, so
a secret reaches agents only when named there.

** sops-guix recipe

[This is a *recipe only*.  The channel ships no =(sops ...)= import and no
companion module: a =(sops ...)= import in the channel's modules would break the
default channel build for users who do not have the extra channel.  The base
service depends on nothing from sops-guix; the generic =secrets-file= also
serves =guix deploy=, a pre-existing =$GC_HOME/secrets.env=, or any other
injection path.]

Add the external channel
(<https://github.com/fishinthecalculator/sops-guix>) to
=~/.config/guix/channels.scm=:

#+begin_src scheme
(cons* (channel
        (name 'sops-guix)
        (url "https://github.com/fishinthecalculator/sops-guix"))
       (channel
        (name 'r0man)
        (url "https://github.com/r0man/guix-channel"))
       %default-channels)
#+end_src

Import the sops module, declare the secret (here the value under the
=gascity/dotenv= key is the whole dotenv blob, written verbatim as a binary),
and wire the decrypted path to =secrets-file=:

#+begin_src scheme
(use-modules (sops services sops))
(use-modules (r0man guix services gascity))

(define gascity-dotenv-secret
  ;; Decrypts the "gascity/dotenv" value of secrets/prod.yaml into a file
  ;; under the sops secrets directory (typically /run/secrets), owned by
  ;; gascity, mode 0400.  The YAML value is the dotenv text itself.
  (sops-secret
   (key '("gascity" "dotenv"))
   (file (local-file "secrets/prod.yaml"))
   (user "gascity")
   (group "gascity")
   (permissions #o400)
   (output-type "binary")))

(operating-system
  ...
  (services
   (append
    (list
     ;; Bring the secret into being at boot (age key derived from the host
     ;; SSH key; see the sops-guix docs for the runbook).
     (service sops-secrets-service-type
              (sops-service-configuration
               (generate-key? #t)
               (host-ssh-key "/etc/ssh/ssh_host_ed25519_key")
               (secrets (list gascity-dotenv-secret))))
     ;; The supervisor loads the decrypted dotenv file on every start.
     (service gascity-service-type
              (gascity-service-config
               (secrets-file (sops-secret->secret-file gascity-dotenv-secret))
               (cities (list (gascity-city-configuration
                              (name "burningswell")))))))
    %base-services)))
#+end_src

=sops-secret->secret-file= returns the decrypted file's path (the sops service
provisions one Shepherd service per secret, named =sops-secret-<key>=), so the
supervisor's wrapper reads exactly what sops wrote.  Encrypted secrets can be
checked into the Guix repository; plaintext never touches disk or the store.

=modify-services= pattern.  When an =operating-system= already carries a sops
service, extend it instead of declaring a second one, and keep the ordering
where sops's one-shot runs before the supervisor.  sops-guix names each secret's
Shepherd service =sops-secret-<key>=, so a service that must wait for one lists
it in its =requirements= (as the sibling worker/observability services do):

#+begin_src scheme
(modify-services %base-services
  (sops-secrets-service-type
   config =>
   (sops-service-configuration
    (inherit config)
    (secrets (cons gascity-dotenv-secret
                   (sops-service-configuration-secrets config))))))
#+end_src

The Gas City service type does not expose an extra-Shepherd-requirement field,
so it cannot itself declare =requirements '(sops-secret-gascity/dotenv)=.  The
recipe relies on ordering that is safe in practice: sops-guix decrypts during
boot activation, the gascity supervisor's provision one-shot runs first, and the
`respawn? #t` supervisor wrapper re-reads =secrets-file= on every (re)start, so
a first-start race self-heals.  If you need a hard requirement, express it where
your own services declare there =requirements=.

* Lifecycle and ownership

The loop runs per supervisor instance; =GC_HOME= is the instance's =gc-home= and
every derived path is keyed off it.  Two phases:

- Activation (root for system, the user for home) materializes *declarative
  files* only: it creates the state, log and =gc-home= directories (=0700=,
  owned by the service user for system), writes each enabled city's generated
  =city.toml= and =pack.toml= (unchanged files are left alone, so a no-op
  reconfigure does not perturb a running controller), copies =files=/=rig-files=
  (preserving executable bits), and writes each instance's =supervisor.toml=
  (=0600=).  It never runs =gc= and never switches user — Guix activation runs
  as root with no =#:user=.
- Provision one-shot (runs as the service user, and the supervisor =requires=
  it) does the *stateful* work per instance: writes =.gc/site.toml=, runs the
  idempotent =gc init --file <city>/city.toml --preserve-existing --no-start
  --skip-provider-readiness= for each city (=genesis?=), optionally runs =gc
  import install --city <city>= (=install-packs?=), then read-merge-writes the
  =cities.toml= registry (=register?=).  It performs no network access unless a
  city opts into =install-packs?=.

Then Shepherd starts the secrets-loading wrapper that =exec=s =gc supervisor
run= as the service user, using the instance's =gc-home=, =XDG_RUNTIME_DIR= and
=port=.

** Idempotent gc init --preserve-existing

Genesis is the idempotent =gc init ... --preserve-existing --no-start
--skip-provider-readiness=, run on *every* one-shot (gated only by =genesis?=).
There is no "=.gc/= exists" gate and no marker: a partial failure leaves the
scaffold in place and the next one-shot converges it, and a failure is visible
in Shepherd status rather than silently skipped.  The generated =city.toml= and
=pack.toml= must exist on disk *before* genesis, which is why the activation
runs first.

** cities.toml ownership

The registry holds =[[cities]]=, =[[rigs]]= and =[[pending_city_requests]]= in
one file, and =gc= rewrites it under an =flock=.  The service writes it with a
locked read-merge-write that replaces exactly the declared and enabled
=[[cities]]= set and preserves everything else verbatim:

| Owned by this service | Owned by =gc= |
|-----------------------+--------------|
| the declared + enabled =[[cities]]= set (path and name) | =[[rigs]]= |
| | =pending_city_requests= |
| | any other section the operator or =gc= adds |

The service deliberately does *not* call =gc register=: on non-systemd-delegated
systems =gc register= regenerates and installs =gc='s own service unit and
starts a supervisor, fighting Shepherd.  A manual =gc register= (or =gc rig
add=) in a service-managed =GC_HOME= is *overwritten* and unsupported — the
declared set is authoritative for =[[cities]]=.

** Removing or disabling a city

The declared-and-enabled set is exactly =[[cities]]=.  Setting =(enabled? #f)=
or removing a city from the list unregisters it (the read-merge-write drops it
and the supervisor reload applies the change) while preserving =[[rigs]]= and
=pending_city_requests=.  Generated files, =.gc/= and =.beads/= are *never*
deleted on disk.  Re-enabling or re-adding a city re-registers it.

** genesis? / install-packs? / register? semantics

| Field | Default | Meaning |
|-------+---------+---------|
| =genesis?= | =#t= | run the idempotent =gc init ... --preserve-existing= for the city |
| =install-packs?= | =#f= | run =gc import install --city <city>= (network-dependent; opt-in so the default system is offline) |
| =register?= | =#t= | include the city in the declared =[[cities]]= set of the instance's registry |

A city with =register? #f= is materialized and genesis-ed but never registered
(useful for a city another supervisor owns).  =install-packs? #t= makes the
supervisor wait on a network fetch; a fetch failure leaves the city visibly down
without failing the system reconfigure.

** Per-instance port rules

Gas City cannot disable its API listener (=[supervisor].port <= 0= resolves to
8372, and a failed bind exits with a port-in-use code, which under Shepherd
would crash-loop).  A lone instance defaults to =8372=; every instance of a
multi-instance value must set =port= explicitly, and two instances that share a
=(bind, port)= — or a =gc-home= — fail closed at evaluation.  Never persist an
ephemeral port.  The service forwards =[supervisor].port= into the generated
=supervisor.toml=.

** Reload and restart

=city.toml=/=pack.toml= changes are picked up by each city controller's own
=fsnotify= watcher; the service does not force city reloads.  It issues =gc
supervisor reload= only when the registry or supervisor settings changed; a
=port=/=bind= change restarts the supervisor instead of reloading.  All of this
is non-fatal, never touches the network, and never drains the session driving
the reconfigure.

* Migrating from burningswell

The existing =burningswell= provisioning in =~/common-lisp/burningswell-cl/.guix=
converges a live city with awk helpers (=converge_kv=, =converge_block=,
=converge_file=) that re-assert declared =city.toml= keys and block regions on
every activation, reloading the controller only when something really changed.

*** This migration is a separate, user-owned change (not performed here)

The actual =burningswell= migration is a *separate, user-owned change outside
this repository*, and was *not* performed by this manual.  It is not part of the
channel and nothing in the channel reads or edits the =burningswell= =/.guix=
tree.  The mapping below is guidance for that future change.

How the awk-converging activation maps onto this service:

| burningswell idiom | Gas City service |
|--------------------+------------------|
| SCAFFOLD phase (stamp-guarded: =gc init=, =gc import install=, =gc rig add=, =gc register=) | the provision one-shot: =gc init --preserve-existing= (=genesis?=), =gc import install= (=install-packs?=), and the locked =[[cities]]= read-merge-write (=register?=); no stamp |
| CONVERGE phase (=converge_kv= restates declared =city.toml= keys every activation) | the declarative generator: activation writes whole generated =city.toml=/=pack.toml= only when they differ; the record is the source of truth |
| =converge_block=/=converge_tree= fenced regions and whole files | =files= / =rig-files= and the typed records; whole files, no fenced markers |
| whole generated files | =city.toml= from the city record, =pack.toml= from the city's =pack= field |
| the list of cities and rigs | the supervisor's =cities= list and each city's =rigs= |
| derived paths (=~/burningswell=, =%gascity-github-token-path=) | =directory=, =gc-home=, =state-directory=, =log-directory=, and =secrets-file= |
| =gc reload --soft= when a key changed | the supervisor reload the one-shot issues when the registry/settings changed; city =city.toml= changes reload via the controller's watcher |
| the city is provisioned by a Home activation | the derived =home-gascity-service-type=, or the system service |

The two-phase split is the same insight: creation and machine-local
registration are one-shot, declarative content is converged every activation.
The service replaces the hand-rolled convergence with generated whole files and
the idempotent =gc init --preserve-existing=.
