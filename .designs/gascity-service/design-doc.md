# Design: a world-class Gas City service for Guix System and Guix Home

Status: **plan / not implemented**
Author: agent session
Last updated: 2026-07-15
Target module tree: `modules/r0man/guix/{services,home/services}/gascity.scm`
plus a new `modules/r0man/guix/toml.scm`.

---

## 0. TL;DR

We add a Guix **system service** and a **derived home service** that run the
machine-wide Gas City supervisor and declaratively materialize **N cities**.
City configuration is written as ordinary Guix records in s-expression form
and compiled to Gas City's `city.toml` / `pack.toml` TOML by a small,
unit-tested TOML emitter that lives in this channel. The typed field surface is
**generated from Gas City's JSON schemas** (committed, CI drift-checked), so
record accessors track the TOML keys mechanically; Phase 1 is
escape-hatch-first and codegen lands in Phase 4 (§12). Three escape hatches keep
us from ever being a straitjacket:

1. `extra-config` — a list of structured TOML nodes merged into the generated
   document (the "proper" escape hatch; still s-expressions, still compiled).
2. `extra-toml` — raw TOML text or a `file-like` appended verbatim (the
   familiar Guix `extra-config` convention).
3. `files` / `rig-files` — arbitrary files copied into the city (or rig)
   directory: prompt templates, formulas, orders, `.mcp.json`,
   `.claude/settings.json`, overlays, scripts.

The system service value is a **list of supervisor instances** (the same
list-of-records shape as `github-actions-runner-service-type`). Each instance
materializes its city directories at activation and provisions the stateful
bits (genesis, registry, optional packs) in a one-shot before running
`gc supervisor run` under shepherd, isolated by its own `GC_HOME`, socket and
API port. One instance is the common case; several are supported natively
(per-user supervisors, a dev/sandbox supervisor beside a production one, and
per-test supervisors in CI/VM tests). The home service reuses the same
records; it inherits `(system->home-service-type gascity-service-type)` and, like
`(r0man guix home services github-actions)`, redefines the
shepherd/activation/profile extensions because the derived type alone is not
sufficient (no account mapping, `/var/...` paths). See §16.4.

## 1. Goals and non-goals

### Goals

- **Complete, with generated records + escape hatches (decided).** The full
  public `City`/pack surface is expressible declaratively. The bulk of the
  ~579 typed fields is *generated* from
  `docs/reference/schema/{city,pack}-schema.json` (committed, CI drift-checked),
  with a hand-maintained override table for tri-state, secret and gexp-aware
  fields. Until codegen lands, every field is reachable through the
  `extra-config`/`extra-toml`/`files` escape hatches; the typed surface is then
  additive. Getting a working service and never drifting are the priorities, in
  that order.
- **Obvious mapping.** Record and field names mirror TOML keys: TOML
  `max_active_sessions` → Scheme `max-active-sessions`; TOML `[daemon]` →
  `<gascity-daemon-configuration>`. One worked example per major section in the
  manual.
- **S-expressions compile to TOML.** The user never writes TOML by hand (unless
  they choose the raw escape hatch). Serialization is deterministic, ordered,
  escaped correctly and unit-tested.
- **World-class Guix service semantics.**
  - a proper service type, `default-value`, `description`, `documentation`;
  - account / group management baked in (system) or user-owned state (home);
  - an idempotent activation that converges existing directories;
  - shepherd one-shot(s) for genesis plus the long-running supervisor;
  - `guix home` derived service with mapping;
  - VM and unit tests wired into `Makefile.am`.
- **Multiple cities** in one service value, each independently enable-able,
  with its own directory, user, package override, registry name and config.
- **Config is generated by Guix; `gc init` only scaffolds state.** The config
  is written by activation; the one-shot runs the idempotent
  `gc init --preserve-existing` to converge `.gc/`/`.beads/`, so no hand-rolled
  convergence or stamp guards are needed.

### Non-goals (for the first complete iteration)

- Reimplementing formula / order file formats as records. Formulas and orders
  are separate specs (formula-spec v1/v2, order files). They are covered by the
  `files` escape hatch in phase 1 and can get first-class records later. The
  plan reserves a `gascity-formula-configuration` and
  `gascity-order-configuration` for a follow-up.
- Hand-writing every leaf config record. The typed field surface is generated
  from the JSON schemas (§12 Phase 4); hand-written records are reserved for
  service/identity structure and the semantic override table.
- Managing a hosted/remote Gas City service (`gc login`, `--city-url`). Local
  cities only.
- Managing the agent CLI credentials (`claude` login, GitHub tokens). Those are
  secrets and belong to the environment / `secrets-file`, not the store (§16.17).
- Replacing the `burningswell` city provisioning logic. Migration is a
  follow-up; this document describes what migration would target.

## 2. Background: how Gas City actually deploys

This section is the mental model the record model is built from. It is derived
from the Gas City docs in `~/workspace/gascity/docs` and the source in
`internal/supervisor`, `internal/config`, `internal/citylayout` and
`cmd/gc`.

### 2.1 The machine-wide supervisor and the registry

- One process per machine, started with `gc supervisor run` (foreground), is
  the canonical control loop. `gc supervisor start` forks it.
- It reads a TOML registry at `~/.gc/cities.toml` (or `$GC_HOME/cities.toml`).
  Shape (`internal/supervisor/registry.go`):

  ```toml
  [[cities]]
  path = "/abs/path/to/city"
  name = "machinelocal-alias"   # optional; defaults to effective city name

  [[rigs]]
  path = "/abs/path/to/rig"
  name = "globally-unique-rig"
  default_city = "/abs/path/to/city"  # optional
  ```

- It also reads `~/.gc/supervisor.toml` (or `$GC_HOME/supervisor.toml`) for its
  own settings (`[supervisor]` port/bind/patrol, `[publication]`,
  `[events.export]`).
- `gc register <path>` writes the registry entry; `gc start <path>` = fetch
  packs + register + ensure supervisor. Both are idempotent.
- The supervisor reconciles every registered city from one process; a city is a
  subprocess/controller it manages. Multiple cities share the machine but are
  isolated by their own tmux socket (default = city name) and their own Dolt
  port (derived from the city path, or pinned in `[dolt]`).

### 2.2 The city directory

A city is a directory that must contain `city.toml`. The canonical layout
(`internal/citylayout`) is:

```
city-root/
  city.toml            # deployment: workspace, providers, rigs, daemon, storage, ...
  pack.toml            # the root pack: [pack], imports, agents, services, globals, ...
  agents/<name>/       # definition convention: agent.toml + prompt.template.md
    agent.toml
    prompt.template.md
  prompts/             # prompt templates and shared fragments
  formulas/            # formula TOML, one file per formula
  orders/              # order TOML, one file per order
  scripts/             # city-local scripts
  skills/              # skill catalog
  mcp/                 # MCP configuration catalog
  commands/            # pack commands (run.sh, command.toml)
  doctor/              # local doctor checks
  overlay/             # pack overlay files
  assets/              # private support files
  .gc/                 # MUTABLE RUNTIME (never in the store)
    site.toml          # machine-local bindings: workspace name/prefix, rig paths
    cache/packs/       # fetched pack cache
    runtime/           # controller runtime state, worktrees, services
  .beads/              # bd/Dolt bead ledger (mutable)
```

Two TOML files carry almost all declarative content:

- **`city.toml`** is *deployment*: `[workspace]`, `[providers.*]`,
  `[upstreams.*]`, `[[agent]]`, `[[named_session]]`, `[[rigs]]`,
  `[rigs.imports.*]`, `[rigs.patches]`, `[patches.*]`, `[storage]`,
  `[beads]`, `[session]`, `[mail]`, `[events]`, `[usage]`, `[dolt]`,
  `[formulas]`, `[daemon]`, `[orders]`, `[api]`, `[chat_sessions]`,
  `[session_sleep]`, `[convergence]`, `[doctor]`, `[maintenance]`,
  `[[service]]`, `[[webhook]]`, `[webhooks]`, `[github]`, `[extmsg]`,
  `[agent_defaults]`, `[[pricing]]`, `[defaults.rig.imports.*]`.
- **`pack.toml`** is *portable definition* and the root pack manifest:
  `[pack]`, `[imports.*]`, `[agent_defaults]`, `[defaults.rig.imports.*]`,
  `[[agent]]`, `[[named_session]]`, `[[service]]`, `[[webhook]]`,
  `[providers.*]`, `[upstreams.*]`, `[runtimes.*]`, `[formulas]`,
  `[patches.agent]`, `[[doctor]]`, `[[commands]]`, `[global]`,
  `[[pricing]]`.

  Per `internal/config/compose.go`, when both exist the root `pack.toml` is
  the base and `city.toml` wins on conflicts. Imports live canonically in
  `pack.toml`; `city.toml` imports are kept only for compatibility.

### 2.3 Machine-local vs declarative state

This split is the single most important fact for the service design:

| Thing | Where it lives | Declarative? |
|---|---|---|
| city/pack config | `city.toml`, `pack.toml` | **yes** |
| workspace name/prefix | `.gc/site.toml` (`workspace_name`, `workspace_prefix`) | machine-local, but derivable |
| rig paths | `.gc/site.toml` `[[rig]] name/path`; `rig.path` in `city.toml` is deprecated | **machine-local** |
| supervisor registry | `~/.gc/cities.toml` | machine-local, but derivable |
| supervisor settings | `~/.gc/supervisor.toml` | **yes** (our record) |
| bead ledger | `.beads/` (Dolt) | mutable, bootstrap once |
| pack cache | `.gc/cache/packs/` | mutable, fetched |
| runtime state | `.gc/runtime/` | mutable |
| Claude hooks | `.claude/` / `hooks/claude.json` | partly generated by `gc init` |

The generator therefore owns `city.toml`, `pack.toml` and auxiliary files, and
the activation owns `.gc/site.toml`, `~/.gc/cities.toml`,
`~/.gc/supervisor.toml` and one-time genesis.

### 2.4 Genesis, and why we still need it

`gc start` requires a city "bootstrapped by `gc init`". `gc init` creates the
`.gc/` scaffold, convention directories, `.claude` hooks, runs `bd init` on the
city ledger, and writes `.gc/site.toml`. `gc init --file <toml>
--preserve-existing --no-start <dir>` validates the supplied TOML, scaffolds
everything *around* a pre-authored `city.toml`/`pack.toml` and does not start
anything. That is the correct genesis primitive for us:

- The per-instance **one-shot** materializes the generated
  `city.toml`/`pack.toml`, then runs
  `gc init --file ... --preserve-existing --no-start --skip-provider-readiness`
  idempotently to create the runtime scaffold and the bead ledger.
- Activation and the one-shot always converge the generated files; genesis runs
  in the one-shot as the service user and is **not** gated on `.gc/` (§16.1,
  §16.7).

This avoids the two failure modes of the current `burningswell` approach
(described in §3): a hand-rolled `gc init` + awk convergence layer, and a
stamp-guarded script that silently does nothing once stamped.

### 2.5 Runtime requirements

`gc` needs `tmux`, `jq`, `git`, `dolt`, `bd`, and `flock` on `PATH`. The
channel's `gascity-next` already propagates `beads-next`, `dolt`, `jq`,
`tmux`, `coreutils`, `grep`, `lsof`, `procps`, `util-linux` and
`python-for-gascity`. Only `git` is not propagated and must be added by the
service profile/PATH. A city whose agents use `claude-code`/`gh` also needs
those on the agent `PATH`; that is an operator concern exposed through the
service's `packages` field.

## 3. Why the existing burningswell implementation is not the model

`~/common-lisp/burningswell-cl/.guix` currently:

- bootstraps the city with an imperative `gc init --template gascity`, then
- **converges** individual keys into `city.toml` with hand-written `awk`
  (`city-converge-kv.awk`, `city-converge-block.awk`, `city-converge.sh`),
- owns whole regions with marker fences, and
- triggers `gc reload --soft` when something changed.

The comments in `homes.scm` are candid that this is a workaround: `converge_kv`
addresses one key in one section and cannot express arrays-of-tables;
withdrawal of a declaration needs `retire_line`/`retire_block`; and a stale
stamp once made the whole thing a no-op. It also provisions exactly one city
and hardcodes `/home/gascity`.

What we keep from it:

- the **scaffold vs converge** distinction (bootstrap once, converge always);
- idempotent convergence (no reload when nothing changed);
- the awareness that `gc reload --soft` must not drain the session driving the
  reconfigure.

What we replace:

- awk key rewriting → **whole generated TOML files** owned by Guix;
- stamp guards → **idempotent `gc init --preserve-existing`** on every one-shot;
- one hardcoded city → a **list of city records**;
- hand-written paths → derived defaults with explicit overrides.

## 4. Architecture overview

```
(r0man guix services gascity)
  gascity-service-type                 ; value = LIST of supervisor instances
    gascity-supervisor-configuration   ; one record per supervisor process
      id:              "prod"          ; unique; suffixes the shepherd service
      package:         <gascity-next>
      user/group:      "gascity"
      gc-home:         "/var/lib/gascity/.gc"   ; registry + supervisor.toml + isolated socket/lock
      state-directory: "/var/lib/gascity"
      log-directory:   "/var/log/gascity"
      port:            8372            ; MUST be distinct per instance
      bind:            "127.0.0.1"
      settings:        <gascity-supervisor-settings-configuration> ; [supervisor]/[publication]/[events]
      packages:        (list git ...)  ; extra PATH entries
      environment-variables
      cities:          (list <gascity-city-configuration> ...)

  gascity-city-configuration           ; one per city
    name, directory, package, user, enabled?
    workspace, providers, upstreams, imports, defaults, agents,
    named-sessions, rigs, patches, storage, beads, session, mail, events,
    usage, dolt, formulas, daemon, orders, api, chat-sessions,
    session-sleep, convergence, doctor, maintenance, services, webhooks,
    webhook-policy, github, extmsg, agent-defaults, pricing
    files, rig-files, extra-config, extra-toml

(r0man guix home services gascity)
  home-gascity-service-type            ; derived from the system type
  home-gascity-configuration           ; same records, re-exported

(r0man guix toml)
  <toml-document>, <toml-table>, <toml-array-of-tables>, <toml-inline-table>
  gexp TOML value kind, toml-document->string (returns a gexp), toml-value?, ...
```

Service behavior, in one sentence per piece:

- **System service extension** contributes, per supervisor instance, one
  `shepherd-service` (`gascity-supervisor`, suffixed with the instance `id`)
  running `gc supervisor run` as `user`, a paired `gascity-provision-<id>`
  one-shot the supervisor requires, an `activation-service-type` extension that
  (a) creates the account + state/log directories and (b) materializes each
  enabled city's generated files (owned by `user`), plus a
  `profile-service-type` extension. The one-shot (running as `user`) writes
  `.gc/site.toml`, runs `gc init --file`, optionally `gc import install`, and
  read-merge-writes `[[cities]]`; `supervisor.toml` is generated too.
- **Home service extension** contributes a user-level
  `home-shepherd-service` per instance running the same command and a matching
  home one-shot, a `home-activation` that materializes cities under
  `$XDG_STATE_HOME/gascity`, and a `home-profile` extension adding the packages.
- Both share **all** record definitions and the **same serializer**; only the
  path defaults and the shepherd user differ. The home service inherits
  `(system->home-service-type gascity-service-type)` but redefines the
  shepherd/activation/profile extensions, as github-actions documents (§16.4).

### 4.1 Multiple supervisors and isolation

Gas City is explicitly designed to let more than one supervisor coexist on a
machine. The isolation key is **`GC_HOME`**. From
`internal/supervisor/config.go` and `cmd/gc/cmd_supervisor.go`:

| Concern | Path / value | Isolated by |
|---|---|---|
| city registry | `$GC_HOME/cities.toml` | `GC_HOME` |
| supervisor settings | `$GC_HOME/supervisor.toml` | `GC_HOME` |
| control socket | `RuntimeDir()/supervisor.sock` | `GC_HOME` |
| instance lock | `RuntimeDir()/supervisor.lock` (flock) | `GC_HOME` |
| runtime/events | `RuntimeDir()/events.jsonl`, provider state | `GC_HOME` |
| API listener | `[supervisor].bind`:`port`, default `127.0.0.1:8372` | **port must be distinct** |
| per-city tmux server | `tmux -L <city-name>`, overridable by `[session].socket` | city name / socket |
| per-city Dolt | port hashed from the **city path** (or pinned `[dolt].port`) | city path |
| controller lock | `<city>/.gc/controller.lock` (flock) | city path |

`RuntimeDir()` is the crux: for the *default* home it is
`$XDG_RUNTIME_DIR/gc`, but for an **isolated `GC_HOME` override** it is the
`GC_HOME` itself, precisely so an isolated supervisor never touches the host
supervisor's socket or lock. This is also why Gas City's own test binaries
*panic* unless `GC_HOME` is set, and why `GC_ISOLATED=1` exists for non-test
sandboxes. Multiple supervisors are therefore a supported, intended mode.

What the service must get right:

1. **`GC_HOME` per instance.** This is the `gc-home` field. It defaults to
   `<state-directory>/.gc` for system instances and `$HOME/.gc` for home
   instances, and must be distinct between instances: two instances that share
   `gc-home` fail closed at evaluation (`XDG_RUNTIME_DIR` is set per instance,
   §16.2, so a shared `gc-home` would otherwise share the supervisor
   socket/lock).
2. **A distinct API port per instance (decided, §13.2).** There is no "disable"
   value (`[supervisor].port <= 0` resolves to `8372`, `GC_SUPERVISOR_DASHBOARD=0`
   only disables the dashboard, and a failed bind exits with the port-in-use
   code; under shepherd that would crash-loop). A lone instance defaults to
   `8372`; a second or later instance must set `port` explicitly, and two
   instances that share `(bind, port)` are rejected at evaluation. A system and
   a home supervisor on the same host must also use distinct ports.
3. **Distinct city identity across instances.** Two instances that both manage
   a city named `foo` would collide on the default tmux socket `-L foo`. Either
   give instances disjoint city names/sets or set `[session].socket`
   explicitly per city. Dolt ports are already disjoint because they hash the
   city path.
4. **Never register the same city directory under two supervisors.** The
   controller lock and bead ledger are per city path; doing so is a user error
   the activation should detect (a directory already claimed elsewhere).

Why this matters beyond tests:

- **Tests / CI.** Each VM or integration test gets its own `GC_HOME` (a temp
  dir) and port, so tests never see the host registry and can run in parallel.
  Our own VM test should exercise exactly this: two instances, one trivial city
  each, asserting both supervisors come up and neither sees the other's city.
- **Home vs system.** `guix home` runs a supervisor as the user under
  `$HOME/.gc`; `guix system` runs one as `gascity` under
  `/var/lib/gascity/.gc`. They coexist with no configuration beyond distinct
  homes/bind ports (and the user instance is naturally isolated by its
  `XDG_RUNTIME_DIR`).
- **Dev beside production.** A sandbox supervisor (`gc-home` on a scratch dir,
  a high port) can run the same city schema without touching the production
  registry or socket.

This is cheap to support because it is mostly a matter of keying every generated
path off `gc-home`, suffixing the shepherd provision name with `id`, and adding
one port field. The extra cost is one uniqueness check and one more VM test
assertion.

## 6. The record model

### 6.1 Conventions

- **`define-record-type*` + explicit `->toml` procedures** (decided, §13.7),
  not `define-configuration`: the TOML emitter and gexp handling are custom
  (§16.5, §16.6). Accessors are `gascity-agent-configuration-name`, etc. A
  single module-wide `(prefix gascity-)` applies only to any generated leaf
  records that still use `define-configuration`.
- Scheme field names are the TOML keys with `_` replaced by `-`; predicates
  keep the `?` (e.g. `tls-options?` → `tls-options` field if it ever exists).
- Optional fields use `maybe-*` so "absent" and "explicitly empty" are
  distinguishable (critical: Gas City uses tri-state booleans and
  presence-aware patches).
- Strings that accept arbitrary content (commands, scripts) are typed
  `maybe-string-or-gexp`. A gexp is a **first-class TOML value kind** in the IR,
  so the serializer splices it with `ungexp` (`#$`) into the emitted gexp; this
  is how operators embed store paths and `file-like` values, following the blog
  post (§7.2, §16.6).
- **Tri-state booleans** (e.g. `inject_assigned_skills`, `emits_permission_warning`)
  get a dedicated `gascity-tri-state` representation with the values
  `'unset`, `#t`, `#f` (or a `maybe-boolean` where `'unset` is the absent
  marker). Serializer emits nothing for `'unset`, `true`/`false` otherwise.
- **String maps** (`env`, `option_defaults`, `formula_vars`) are alists
  `(("KEY" . "value") ...)` serialized as TOML inline tables.
- **Ordered lists of strings** are Scheme lists and serialize to TOML arrays.
- Every field's docstring is written so `guix home`/`guix system` `describe`
  output is useful, and so the generated manual can be a faithful mapping
  table.

### 6.2 Top-level service records

| Record | Role |
|---|---|
| `<gascity-supervisor-configuration>` | one supervisor instance: `id`, package, user/group, `gc-home`, state/log dirs, bind, `port`, settings, extra packages, environment, cities. The **service value is a list** of these. |
| `<gascity-supervisor-settings-configuration>` | the `~/.gc/supervisor.toml` document: `[supervisor]`, `[publication]`, `[events.export]` |
| `<gascity-city-configuration>` | one city: identity + all `City` fields + files/escape hatches |
| `<gascity-pack-configuration>` | the root `pack.toml` (optional; when omitted, a minimal `[pack]` is generated) |

### 6.4 The root pack record

Gas City splits definition (`pack.toml`) from deployment (`city.toml`). The
service exposes **both**, because pretending they are one file would fight the
tool. Options, in order of recommendation:

- **Recommended:** `<gascity-city-configuration>` has a `pack` field of type
  `<gascity-pack-configuration>`. The service writes the pack document to
  `pack.toml` and the deployment document to `city.toml`. Imports, agents,
  named sessions, providers, upstreams, services, globals, pricing and
  `patches.agent` can appear in either; when a field is set in both, the city
  value wins, matching Gas City's own composition.
- A convenience: fields that Gas City accepts in `city.toml` are also on
  `<gascity-city-configuration>`, and the service **automatically routes** a
  shared field to the pack file if `pack` is absent? No — this creates a
  non-obvious split. Instead, document clearly which record owns which file and
  let `gc config show` (which merges both) be the source of truth.

The plan recommends the first option: two explicit sub-records, one per file.
This is the most faithful and the least surprising. A shorthand constructor can
still make the common case pleasant:

```scheme
(gascity-city-configuration
 (name "burningswell")
 (directory "/var/lib/gascity/burningswell")
 (pack (gascity-pack-configuration
        (imports `(("gc" . ,(gascity-import ...)))))
        (agents (list ...)))
 (workspace (gascity-workspace-configuration
             (provider "claude")))
 ...)
```

## 7. Compiling s-expressions to TOML

### 7.1 Why not reuse `serialize-configuration`

`(gnu services configuration)`'s `serialize-configuration` concatenates each
field's serializer output, in declaration order, into one string. That works for
YAML (the blog post) because YAML is indentation-flexible and has no
"table already defined" rule. TOML is stricter:

- `[a]`/`[a.b]` may only be defined once; duplicate table headers are errors;
- once `[a.b]` is opened, you cannot add a bare key back to `[a]`;
- `[[a]]` arrays-of-tables must be emitted before any `[a.x]` that should attach
  to the *last* element, and `[a.x]` after `[[a]]` attaches to that last element;
- keys inside a table must precede its sub-tables.

String concatenation in declaration order is therefore brittle. We keep
`define-configuration` for the record ergonomics but provide our **own**
document builder and emitter.

### 7.2 TOML intermediate representation (IR)

`(r0man guix toml)` defines:

```scheme
;; A TOML value is one of:
;;   string | boolean | exact integer | inexact real
;;   gexp                                   -> "..." spliced as-is (§7.3)
;;   (toml-array VALUE ...)                 -> [ V, V, ... ]
;;   (toml-inline-table (KEY . VALUE) ...)  -> { KEY = VALUE, ... }
;;
;; A TOML field is (KEY . VALUE).
;;
;; A TOML node (ordered) is one of:
;;   <toml-field>                           -> KEY = VALUE
;;   (toml-table KEY NODE ...)              -> [KEY] then NODE...
;;   (toml-array-of-tables KEY ELEMENT ...) -> [[KEY]] per ELEMENT
;;          where ELEMENT is a list of nodes (fields + nested tables)
;;
;; A document is an ordered list of nodes.
```

Public constructor helpers: `toml-field`, `toml-table`, `toml-array-of-tables`,
`toml-inline-table`, `toml-array`, `toml-document`. `toml-document->string`
returns the final **gexp** (§7.3); there is no plain-string-only sibling.

Each record's serializer is a procedure `(field-name value) -> gexp`
(satisfying `define-configuration`'s `serializer` slot), building zero or more
TOML fragments with `#~`/`ungexp` (`#$`) so store paths and gexps can be
spliced in. A generated `TYPE->toml-document` walks `TYPE-fields` and
concatenates each field's gexp in order (and its own header node), so
**declaration order in the record is the emission order**, which is exactly the
control we need.

### 7.3 Emitter algorithm

`toml-document->string` returns a **gexp** that lowers to the TOML text (the
name is retained, §16.6): it performs a single depth-first walk over a
normalized tree, wrapping literal fragments in `#~`/`ungexp` so spliced values
survive.

1. **Normalize.** Group sibling fields, tables and array-of-tables by key.
   Reject duplicate scalar keys (a programmer error), *unless* an escape hatch
   deliberately overrode them (see §7.5).
2. **Emit a table at path P**: write its scalar/array/inline fields first, each
   as `key = value`; then, in key order, recurse into normal child tables
   (`[P.key]`); then, in key order, emit array-of-tables (`[[P.key]]`), where
   each element emits its own scalars and recurses into its child tables as
   `[P.key.sub]` (attaching to the last element, which is correct TOML).
3. **Root** is a table at the empty path; `[workspace]` etc. are its children.
4. **Values**: basic strings with full escaping; a **gexp value is emitted
   as-is between the surrounding quotes** (`"` `#$value` `"`) with no further
   escaping; `true`/`false`; integers in decimal; floats via a formatter that
   always includes a decimal point or exponent; arrays as `[a, b]`; inline
   tables as `{ k = v, ... }`.
5. **Key quoting**: bare keys match `[A-Za-z0-9_-]+`; anything else (provider
   names with dots, map keys) is emitted as a quoted basic string.

Correctness of TOML ordering is the entire reason for this layer, so it gets
its own unit-test file with golden documents and, if feasible, a
property-style round-trip against a TOML parser (none is available in Guix, so
the *validation* test is delegated to `gc config show --validate`, §10).

**Escaping boundary (limitation).** Only literal string fragments are escaped,
and they are escaped at build time. A spliced gexp value is inserted verbatim
between the quotes of the surrounding basic string, so the operator is
responsible for embedding content that needs no further escaping (a store
path, or an already-escaped fragment). Because the result is a gexp,
golden-string tests compare `(eval-gexp (toml-document->string doc))` against an
expected TOML string, using Guix's own `eval-gexp` helper (§10).

### 7.4 Serializer helpers

A small set of shared helpers, mirroring the blog post's `serialize-field`.
Every helper returns a **gexp** (a TOML fragment), not a plain node list:

| Helper | Emits |
|---|---|
| `gascity-serialize-string` | `key = "value"` |
| `gascity-serialize-maybe-string` | nothing for `'unset`, else string |
| `gascity-serialize-boolean` / `maybe-boolean` | `true`/`false` |
| `gascity-serialize-tri-state` | nothing / `true` / `false` |
| `gascity-serialize-integer` / `maybe-integer` | decimal |
| `gascity-serialize-real` / `maybe-real` | decimal float |
| `gascity-serialize-list-of-strings` | `key = ["a", "b"]` |
| `gascity-serialize-string-map` | `key = { "K" = "v", ... }` |
| `gascity-serialize-string-or-gexp` | `key = "…"`, `#$`-spliced when a gexp |
| `gascity-serialize-subtable NAME PROC` | `[key]` header + sub-document |
| `gascity-serialize-subtables NAME PROC` | `[[key]]` per record |
| `empty-serializer` | nothing (package fields) |

### 7.5 Escape hatches

Three, with explicit precedence. All of them are documented as "you are leaving
the curated surface".

1. **`extra-config`** — a list of TOML nodes (using the public IR constructors)
   merged into the generated document as a **final layering pass**. Fields
   match by full TOML key; an `extra-config` field **replaces** a generated
   field of the same key, and an `extra-config` table merges recursively.
   This is the escape hatch that is still "written in s-expressions and
   compiled into TOML", so it is the recommended one. Its IR nodes may carry
   gexp values (§7.2) exactly like generated fields; the escaping boundary of
   §7.3 applies to them too.
2. **`extra-toml`** — either a string or a `file-like` of raw TOML appended
   verbatim at the end of the generated file. This is the familiar Guix
   `extra-config` convention and lets an operator paste a fragment from the Gas
   City docs. Document the limitation loudly: verbatim append cannot add keys
   to a table the generator already emitted (TOML duplicate-table error); it is
   for whole new tables.
3. **`files` / `rig-files`** — `(destination . file-like)` pairs copied into
   the city directory (`rig-files` into the rig directory). This is how
   prompt templates, shared fragments, formulas, orders, skills, MCP config,
   scripts and overlays are supplied in phase 1. Destinations are relative to
   the city root and may not escape it.

There is deliberately **no** "whole city.toml as a raw file" escape hatch in
phase 1. If an operator needs that, they should not use the record surface;
adding a `raw-config` field that silently disables the rest is a footgun. We
revisit this only if a real corpus (e.g. the gascity examples) cannot be
expressed through records + escape hatches.

### 7.6 Idempotency

The generator is pure: same records in, same bytes out. The activation copies a
generated file into place only when its contents differ from what is on disk
(compare with `file=?`/`textual-file?` semantics or a byte compare), so a
reconfigure that changes nothing does not touch `city.toml` and does not
perturb a running controller.

## 8. City lifecycle (system and home share the algorithm)

The loop below runs **per supervisor instance** in
`<gascity-supervisor-configuration>`; `GC_HOME` is the instance's `gc-home`
and every derived path is keyed off it.

`gascity-city-configuration` fields used by the activation:

- `name` (required, unique, `[A-Za-z0-9._-]+`, also the registry name),
- `directory` (default derived),
- `enabled?` (default `#t`),
- `package` (default: the service package),
- `user` (default: the service user),
- `genesis?` (default `#t`) — whether to bootstrap `.gc/`/`.beads`,
- `install-packs?` (default `#f`) — when `#t`, run `gc import install` in the
  per-instance one-shot; off by default so the system stays offline unless
  opted in,
- `register?` (default `#t`),
- `files`, `rig-files` (destination → file-like).

Pseudo-algorithm. Steps 1–2 run in the activation (root for system, user for
home); steps 3–5 run in the per-instance one-shot as the service user:

```
for each enabled city C:
  dir = C.directory
  # --- activation: materialize generated files ---
  mkdir -p dir; chown user:group dir
  install-generated!  dir/city.toml        (C -> city.toml)
  install-generated!  dir/pack.toml        (C.pack -> pack.toml)   # if present
  install-files!      dir                  C.files + C.rig-files
  # --- per-instance one-shot, as service user ---
  write-site-binding! dir/.gc/site.toml  {workspace_name, workspace_prefix,
                                          [[rig]] name/path/prefix}
  run: gc init --file dir/city.toml --preserve-existing --no-start
       --skip-provider-readiness        (idempotent; gated by C.genesis?, §16.7)
  if C.install-packs?:
     run: gc import install --city dir  (fail-visible; supervisor requires it)
  if C.register?:
     read-merge-write [[cities]] in <GC_HOME>/cities.toml
       (replace only the declared+enabled set; preserve [[rigs]]/pending)
write-generated! <GC_HOME>/supervisor.toml  (one-shot)
```

Then shepherd starts `gc supervisor run` as the service user.

Notes and decisions:

- **Why write `cities.toml` directly instead of `gc register`?** `gc register`
  calls `ensureSupervisorRunning`, which on non-systemd-delegated systems
  regenerates and installs `gc`'s own service unit and starts a supervisor —
  fighting shepherd. Instead, the one-shot does a locked **read-merge-write**
  that replaces only the declared+enabled `[[cities]]` set and preserves
  `[[rigs]]`/`pending_city_requests` (§16.3). Removed/disabled cities are
  unregistered, not deleted on disk (§13.17). A manual `gc register` in a
  service-managed `GC_HOME` is overwritten and unsupported.
- **`gc init` needs the generated `city.toml` on disk already**; activation
  materializes it before the one-shot runs. With `--preserve-existing` and
  `--no-start`, `gc init` does not overwrite our files and converges the
  scaffold idempotently.
- **If genesis fails** (e.g. `dolt` unavailable), the one-shot fails loudly and
  the supervisor does not start, matching the `burningswell` lesson that an
  unprovisioned city must be impossible to miss. The generated files remain on
  disk and the next one-shot retries.
- **`gc import install` is network-dependent (decided, §13.5).** It is an
  opt-in per-instance one-shot (`install-packs? #f`), so the default system is
  offline. When enabled, the supervisor requires the one-shot, and a failed
  fetch leaves the city visibly down without failing the system reconfigure.
  The supervisor only refreshes builtin/legacy packs, not remote `[imports.*]`,
  so when the one-shot is disabled the operator must pre-populate
  `$GC_HOME/cache/repos` or vendor the packs.
- **Reload on change (decided, §13.6).** `city.toml`/`pack.toml` changes are
  picked up automatically by each city controller's fsnotify watcher
  (`cmd/gc/controller.go`); the service does not force city reloads. It issues
  `gc supervisor reload` only when `cities.toml` or `supervisor.toml` changed
  (registry reconciliation); a `port`/`bind` change restarts the supervisor
  instead of reloading. All of this is non-fatal, never touches the network,
  and must not drain the session driving the reconfigure.
- **Account and directories (system only):** activation creates the `gascity`
  account/group if absent (via the same `user-account`/`user-group` records as
  `github-actions`), then `chown`s the state dir, log dir, city dirs and
  materialized files to `gascity:gascity` (activation runs as root; §16.1).
  Modes: state/city dirs `0700`, `supervisor.toml`/`cities.toml`/`secrets.env`
  `0600`. The account's home defaults to the state directory.

### 8.1 Activation, provisioning and supervisor programs

Three `program-file`s, built with `with-imported-modules`:

- `gascity-activation-program` (activation, root for system / user for home) —
  the file-materialization steps of the loop: create/chown dirs, write the
  generated `city.toml`/`pack.toml`/`files`, and write `supervisor.toml`. Pure
  data in, files out.
- `gascity-provision-program` (one-shot, runs as `user`) — the stateful steps:
  write `.gc/site.toml`, run idempotent `gc init --file ... --preserve-existing
  --no-start --skip-provider-readiness`, run `gc import install` when enabled,
  and read-merge-write `[[cities]]`. Sets `HOME`, `GC_HOME`, `XDG_RUNTIME_DIR`,
  `PATH`, `SSL_CERT_DIR`/`SSL_CERT_FILE` and `GUIX_*`. It refers to `gc` by
  store path (`#$gascity`), never by name.
- `gascity-supervisor-program` (long-running) — a wrapper that loads
  `secrets-file` into the environment and `exec`s `gc supervisor run` (§16.17).

All must be pure functions of their inputs so the same code runs under
`guix system reconfigure`, `guix home reconfigure`, and a service restart.

## 9. Shepherd service

### 9.1 System

```scheme
;; One such service per <gascity-supervisor-configuration>; ID suffixes the
;; provision name so instances can coexist.
(let ((id (gascity-supervisor-configuration-id config)))
  (shepherd-service
   (provision (list (string->symbol
                     (if id (string-append "gascity-supervisor-" id)
                         "gascity-supervisor"))))
   ;; The provision one-shot runs genesis/packs/registry as the service user.
   (requirement `(user-processes networking
                  ,(string->symbol
                    (if id (string-append "gascity-provision-" id)
                        "gascity-provision"))))
   (documentation "Run a Gas City machine-wide supervisor (gc supervisor run).")
   (start #~(make-forkexec-constructor
             ;; Wrapper loads secrets-file into the env, then execs gc.
             (list #$(gascity-supervisor-program package gc-home secrets-file))
             #:user #$user #:group #$group
             #:directory #$home
             #:log-file #$(string-append log-directory "/supervisor"
                                        (if id (string-append "-" id) "")
                                        ".log")
             #:environment-variables
             #~(list (string-append "HOME=" #$home)
                     (string-append "GC_HOME=" #$gc-home)
                     (string-append "XDG_RUNTIME_DIR=" #$gc-home)
                     "GC_SUPERVISOR_PRESERVE_SESSIONS_ON_SIGNAL=1"
                     (string-append "PATH=" #$path)
                     ...)))
   (stop #~(make-kill-destructor))
   (respawn? #t)))
```

Each instance gets its own `<gc-home>/supervisor.toml` carrying its `bind` and
`port` (a lone instance defaults to `8372`; extras must be explicit, §13.2), so
no two instances bind the same `(bind, port)`. The `gascity-supervisor-<id>`
service **requires** the paired one-shot `gascity-provision-<id>`: genesis,
site binding, registry and optional pack fetching run as the service user
before the supervisor starts, and are retried on restarts. Activation only
materializes files (§16.1). Start the supervisor through the secrets-loading
wrapper (§16.17), not `gc` directly, and set `XDG_RUNTIME_DIR` per instance
(§16.2).

### 9.2 Home

Same command, no `#:user`/`#:group`, no `networking`/`user-processes`
requirement, log under the home state directory, `GC_HOME` under `$HOME`. Use
`home-shepherd-service-type`, `home-activation-service-type` and
`home-profile-service-type`, and `define-service-type-mapping` from
`gascity-service-type` to `home-gascity-service-type`. As github-actions
documents (§16.4), **inherit `(system->home-service-type …)` but redefine the
extensions** — the derived type alone drops accounts and hardcodes `/var/...`.
Concretely, the dropped system extensions are `account-service-type` (a Home
environment has no system accounts), `shepherd-root-service-type`,
`activation-service-type` (root file materialization and `chown` under
`/var/lib`) and `profile-service-type`; they are replaced by
`home-shepherd-service-type`, `home-activation-service-type` and
`home-profile-service-type`, as github-actions does. The home service
re-exports every record and accessor so a user can write
`home-gascity-service-type` configs without importing the system module.

## 10. Testing strategy

1. **Emitter unit tests** (`gascity-toml.scm`): escaping, bare vs quoted keys,
   integer/float formatting, arrays, inline tables, normal nested tables,
   arrays-of-tables, nested tables under an array element, gexp splicing, and
   golden documents. Because `toml-document->string` returns a gexp, golden
   tests reduce it with `eval-gexp` (below) before comparing.
2. **Record/serialization unit tests** (`gascity.scm`): construct a
   comprehensive city, serialize, compare to a golden `city.toml`; test
   `maybe-*`, tri-state, string maps, escape hatches and precedence.
3. **Gas City validation test**: build a temp city directory, write the
   generated `city.toml`/`pack.toml`, and run
   `gc config show --validate --city <dir>` from the `gascity-next` package.
   This is the strongest correctness signal available and needs no network if
   only builtin imports are used. Gate it so it is skipped if the binary cannot
   run in the build sandbox (it should, being pure parsing).
4. **System VM test**: `operating-system` with `gascity-service-type` and **two
   supervisor instances** (each with its own `gc-home`, port and one trivial
   city, plus one instance with no external packs); assert both
   `gascity-supervisor-<id>` services are running, each `<gc-home>/cities.toml`
   lists only its own city, the two instances' `supervisor.sock` and
   `supervisor.lock` paths are distinct, and neither instance sees the other's
   registry. Register in `SYSTEM_TEST_FILES`.
5. **Home test**: assert the generated `city.toml`, site binding, registry and
   home shepherd extension, and assert that adding a system
   `gascity-service-type` configuration to a home environment maps to the home
   service type.

Golden-string comparison uses the same `eval-gexp` trick as Guix's own
`tests/services/configuration.scm`, so the emitter stays a gexp while tests
compare plain strings:

```scheme
(define (eval-gexp x)
  (eval (gexp->approximate-sexp x) (current-module)))

(test-equal "golden city.toml"
  expected-toml
  (eval-gexp (toml-document->string (gascity-city->toml-document city))))
```

Quality gates for the implementing session: `make check`, `guix style`/`guix
lint` on the new modules, and the VM test when the environment allows.

## 13. Open questions, decisions and review findings

Status legend: **decided** (locked in this revision), **confirmed** (verified
against the Gas City source), **review** (engineering finding with required
changes in §16 — applied by the implementer, not an open user decision). All
operator-level decisions are now made: §13.1, 2, 4, 5, 6, 7, 9, 10, 11, 16, 17
are **decided**; §13.3, 12–15, 18–21 are **review** engineering fixes; §13.8 is
a Phase 3 build verification.

1. **Service value shape (decided).** The service value is a **list of
   `<gascity-supervisor-configuration>` records**, one per supervisor process,
   matching `github-actions-runner-service-type` and natively supporting the
   multiple-supervisor isolation described in §4.1. Add a default value and a
   `(gascity-service-config ...)` helper so the common one-instance case is not
   a one-element list (§16.15).
2. **API port allocation (decided).** The API listener cannot be disabled
   (`[supervisor].port <= 0` resolves to `8372`; `GC_SUPERVISOR_DASHBOARD=0`
   only disables the dashboard plane). A lone instance defaults to `8372`; any
   additional instance must set `port` explicitly, and duplicate `(bind, port)`
   fails closed at evaluation. Document that a system supervisor and a home
   supervisor on the same host must use distinct ports (they share the network
   namespace). Never persist an ephemeral port.
3. **`cities.toml` ownership (review, §16.3).** We write the registry directly
   (correct — `gc register` would install and start its own supervisor, see
   §16.3), but the file also holds `[[rigs]]` and `pending_city_requests`, which
   `gc` maintains under a lock. Re-convergence must be a locked read-merge-write
   that replaces only the declared `[[cities]]` set; a wholesale Guix write
   clobbers rigs and in-flight requests.
4. **Genesis (decided).** Run the idempotent
   `gc init --file … --preserve-existing --no-start --skip-provider-readiness`
   from the per-instance one-shot (as the service user, §16.1), controlled by
   `genesis?` (default `#t`). No "`.gc/` exists" gate and no marker: a failure
   is retried on the next one-shot run and is visible in shepherd status.
5. **Pack fetching (decided).** Only `gc import install` clones remote
   `[imports.*]` packs; the supervisor refreshes only builtin/legacy packs, so
   "lazy at first reconcile" is not a safe default. Provide an **opt-in**
   per-instance one-shot (`install-packs? #f`). When enabled, the supervisor
   requires the one-shot and fetch failure leaves the city visibly down without
   failing the system reconfigure; when disabled, the operator pre-populates
   `$GC_HOME/cache/repos` or vendors packs.
6. **`reload` behavior (decided).** The city controller already fsnotify-watches
   `city.toml`/includes and reloads (normal drift rules), so the service does
   not force city reloads. It issues `gc supervisor reload` only when the
   registry or supervisor settings changed; a `port`/`bind` change restarts the
   supervisor. Non-fatal, no network, never drains the reconfigure-driving
   session.
7. **`define-record-type*` + explicit `->toml` (decided).** Because the TOML
   emitter and gexp handling are custom (§16.5, §16.6), hand-written and
   generated records use plain `define-record-type*` with explicit `->toml`
   procedures (the `github-actions.scm` style), not `define-configuration`.
8. **Generated `pack.toml` vs `gc init` writing its own (build verification).**
   `gc init` writes a `pack.toml` when `--preserve-existing` is not enough; we
   always pass `--preserve-existing`, so our generated pack must exist *before*
   genesis. Verified by the Phase 3 validation test.
9. **Directory-convention content (decided).** Formulas/orders/skills/prompts
   stay out of the typed surface for now and are supplied via `files`. A
   mutually-exclusive `raw-city-toml`/`raw-pack-toml` escape hatch is not
   included; `extra-config` plus codegen covers the field surface (§12 Phase 4).
10. **Schema-driven codegen (decided, §16.13).** The typed field surface is
    generated from `docs/reference/schema/{city,pack}-schema.json` (committed,
    CI drift-checked) with a hand-maintained override table for tri-state,
    secret and gexp fields. Phase 1 is escape-hatch-first; codegen is §12
    Phase 4.
11. **Secrets (decided).** Literal secrets must never be part of the Guix
    configuration (store, system config, or the shepherd
    `environment-variables`). The generated TOML may contain only `$VAR`
    references; values are injected into the supervisor environment at runtime
    from a `secrets-file`. Add a `sanitize`/lint guard that rejects obviously
    literal secrets. sops-guix is integrated by **documented recipe only**
    (§16.17); the base module stays free of `(sops …)` and provides the generic
    `secrets-file`.
12. **Privilege and ownership (review, §16.1).** System activation runs as root
    and has no `#:user`; genesis must run from the one-shot. File modes and
    ownership are otherwise unspecified.
13. **Socket isolation (review, §16.2).** `XDG_RUNTIME_DIR` can defeat `GC_HOME`
    socket isolation. Enforce uniqueness on `gc-home` as well as `(bind, port)`,
    and set `XDG_RUNTIME_DIR` per instance.
14. **Derived home service (review, §16.4).** `system->home-service-type` alone
    is insufficient (the sibling `github-actions` module says so in a comment);
    the extensions must be redefined explicitly.
15. **Serializer prefix (review, §16.5).** Use one module-wide `(prefix
    gascity-)`; a per-record prefix is incompatible with shared
    `gascity-serialize-*` helpers.
16. **Gexp embedding in the IR (decided, §16.6).** The emitter is fully
    gexp-aware: a gexp is a first-class TOML value kind, serializers return
    gexps (not node lists), and `toml-document->string` itself returns a gexp
    (§7.2–§7.4).
17. **Removal / disabling a city (decided).** `cities.toml` `[[cities]]` is
    exactly the declared+enabled set; removed/disabled cities are unregistered
    (preserving `[[rigs]]`/`pending_city_requests`) and applied via the
    supervisor reload; generated files and `.gc/`/`.beads/` are never deleted.
    A manual `gc register` in a service-managed `GC_HOME` is overwritten
    (documented as unsupported).
18. **`include`/`includes` (review, §16.9).** Present in the schema and missing
    from the inventory.
19. **`extra-toml` ordering (review, §16.10).** Verbatim append cannot add root
    scalars or extend existing tables.
20. **`extra-config` merge placement (review, §16.11).** Do precedence as a
    pre-emission pass, not inside the emitter.
21. **`files` / `rig-files` naming (decided).** `files` is city-root,
    `rig-files` is rig-root (§16.12); the old `extra-files` name and the
    §7.5/§8 contradiction are removed.

## 16. Design review findings and required corrections

Added by a design review on 2026-07-15 against the Gas City source at
`~/workspace/gascity` (registry/config/layout/compose, `cmd/gc`), the generated
`docs/reference/schema/{city,pack}-schema.json`, and the sibling
`github-actions` system/home modules. Each item maps to the numbered item in
§13 that references it. Items 16.1–16.7 are implementation-blocking; resolve
them before Phase 1 as written.

### 16.1 Genesis in the activation path cannot run as the service user (blocking)

System activation scripts run as **root**, and Guix activation gexps have no
`#:user`. §8/§8.1 runs `gc init` "as `C.user`" but never says how. As written,
`.gc/`, `.beads/`, `cities.toml`, `supervisor.toml` and the city directories are
root-owned, and the `gascity` supervisor cannot write them.

**Fix:** move genesis (and `gc import install`) into the per-instance one-shot
shepherd service, which supports `#:user`. Keep the activation for
root-materialized declarative files only, then `chown -R user:group` the state
and city directories before the one-shot runs. Make the one-shot the *only*
genesis path (the activation should not run `gc init` at all).

### 16.2 `XDG_RUNTIME_DIR` can defeat `GC_HOME` socket isolation (blocking)

`RuntimeDir()` (`internal/supervisor/config.go`) returns `GC_HOME` only when
`GC_HOME` is an isolated override; otherwise it uses `$XDG_RUNTIME_DIR/gc`. With
`XDG_RUNTIME_DIR` present in a system instance's environment, two instances for
the same user share `$XDG_RUNTIME_DIR/gc/supervisor.sock` and `supervisor.lock`.
The §4.1 isolation table implies `GC_HOME` alone is sufficient.

**Fix:** set `XDG_RUNTIME_DIR` explicitly per instance (to `gc-home` or a
per-instance dir), and make the service reject two instances that share
`gc-home` as well as `(bind, port)`. The VM test must assert the actual socket
and lock paths differ, not just the registry contents.

### 16.3 Direct `cities.toml` writes clobber `[[rigs]]` / `pending_city_requests` (blocking)

`Registry` stores `[[cities]]`, `[[rigs]]` and `[[pending_city_requests]]` in one
file, and `saveLocked` deliberately preserves the latter two under an flock
(`internal/supervisor/registry.go`). A Guix-generated document containing only
`[[cities]]` deletes rig registrations and in-flight request records, and races
the running supervisor's own atomic rewrite.

The decision to avoid `gc register` is **correct**: `gc register` calls
`ensureSupervisorRunning`, which on non-systemd-delegated systems regenerates
and installs `gc`'s own service unit and starts a supervisor
(`cmd/gc/cmd_supervisor_city.go:410`, `cmd/gc/cmd_supervisor_lifecycle.go:730`) —
it would fight shepherd. (There is a `GC_SUPERVISOR_SYSTEMD_UNIT` delegation
opt-in, but it is systemd-only and does not apply to Guix.)

**Fix:** implement a read-merge-write that replaces only the declared
`[[cities]]` set, preserves `[[rigs]]`/`pending_city_requests`, and writes via a
temp file + `rename` under the same flock pattern as `Registry.saveAllLocked`.
Document the ownership contract: what Guix owns, what `gc` owns, and what
happens after `gc register`/`gc unregister`/`gc rig add`.

### 16.4 `system->home-service-type` alone is insufficient (blocking)

§0/§9.2 claims the home service is produced by `system->home-service-type` +
`define-service-type-mapping`, "exactly the convention already used by
github-actions". But `modules/r0man/guix/home/services/github-actions.scm:125-137`
explicitly overrides all extensions: the derived type has no
`account-service-type` mapping, the system shepherd/activation hardcode a
dedicated user and `/var/...` paths, etc. Gas City will hit the same issues.

**Fix:** derive and inherit, but redefine `home-shepherd-service-type`,
`home-activation-service-type` and `home-profile-service-type` explicitly (as
github-actions does), and enumerate which system extensions are intentionally
dropped.

### 16.5 Serializer prefix contradiction (blocking)

`define-configuration` resolves a field's default serializer as
`PREFIXserialize-TYPE` (`gnu/services/configuration.scm:279-281`). §6.1 proposes
a *per-record* prefix (e.g. `gascity-agent-`) while §7.4 defines *shared*
helpers named `gascity-serialize-*`. These cannot compose without duplicating a
serializer per record.

**Fix:** use a single module-wide `(prefix gascity-)`. Accessors are still
`<record-name>-<field>`, so the §6.1 accessor-naming claim is unaffected. Use
explicit `(serializer …)` only where a shared helper must be overridden.

### 16.6 Gexp embedding in the IR (decided)

§7.2 had serializers return plain-data node lists while §6.1 said
`maybe-string-or-gexp` fields are "serialized through `ungexp`". A plain node
cannot hold a store path or gexp. The blog's central technique is that
serializers return gexps so `file-like` objects can be embedded.

**Decided: fully gexp-aware emitter.**

- A **gexp is a first-class TOML value kind**, alongside string/boolean/integer/
  real, arrays and inline tables (§7.2 value grammar).
- Serializers return **gexps** (not plain node lists), blog-post style, building
  fragments with `#~`/`ungexp` (`#$`) (§7.2, §7.4).
- `toml-document->string` itself returns a **gexp** that lowers to the TOML text
  (name retained). There is no plain-string-only sibling; callers use it in gexp
  position (`program-file`, activation, `#~`).
- **Escaping boundary:** literal string fragments are escaped at build time; a
  spliced gexp value is inserted as-is between the surrounding quotes, and the
  operator is responsible for embedding store paths/fragments that need no
  further escaping. This limitation is documented in §7.3.
- **Unit tests** reduce the gexp with Guix's own `eval-gexp`
  (`(eval (gexp->approximate-sexp x) (current-module))`, exactly as
  `tests/services/configuration.scm` does) and compare to a golden TOML string
  (§10.1/§10).

### 16.7 Genesis (decided, §13.4)

`gc init` creates `.gc/` early; a partial failure leaves `.gc/` present and
later activations skip genesis forever. §13 item 4 half-recognizes this.

**Decided:** run the idempotent
`gc init --file … --preserve-existing --no-start --skip-provider-readiness` on
every one-shot (as the service user, per §16.1), gated only by `genesis?`
(default `#t`). No `.gc/`-existence gate and no marker; `gc init` converges the
scaffold, and a failure is retried and visible in shepherd status.

### 16.8 Removal / disabling a city (decided)

`(enabled? #f)` or removing a city from the record list previously left it
registered and managed. **Decided:** the declared+enabled set is authoritative
for `[[cities]]`; the locked read-merge-write from §16.3 unregisters removed or
disabled cities (leaving `[[rigs]]`/`pending_city_requests` intact), and the
supervisor reload from §13.6 applies it. Generated files, `.gc/` and `.beads/`
are never deleted. A manual `gc register` in a service-managed `GC_HOME` is
overwritten and documented as unsupported.

### 16.9 `include`/`includes` missing from the inventory

`City.include`, `Workspace.includes` and `Rig.includes` exist in the schema and
change loader behavior (`internal/config/compose.go`). Either model them or add
an explicit exclusion note; the "comprehensive" goal currently overstates
coverage.

### 16.10 `extra-toml` verbatim append is more restricted than stated

Appending raw TOML after a generated document can only add *new tables*: a
root-level scalar cannot follow a table header, and existing tables cannot be
extended. The doc mentions the duplicate-table case but not this constraint.

### 16.11 `extra-config` merge placement

The emitter's normalization step is described as rejecting duplicate keys
"unless an escape hatch overrode them", which makes the emitter non-pure and
format-aware. Perform the precedence merge as an explicit pre-emission pass that
produces a clean node tree; the emitter should always reject duplicates.

### 16.12 `files` / `rig-files` naming (decided)

§7.5 and §8 disagreed on where `extra-files` landed. **Decided:** the fields
are `files` (copied under the city root) and `rig-files` (copied under the rig
root); §7.5 and §8 have been updated.

### 16.13 Schema-driven codegen (decided, §13.10)

`city-schema.json` has ~70 types and several hundred fields, and Gas City's
schema is auto-generated and moving fast. Hand-maintaining a
`define-configuration` mirror plus serializers is a permanent tax; a reactive
drift test is not enough.

**Decided:** generate the leaf records from
`docs/reference/schema/{city,pack}-schema.json` (committed + CI-regenerated
check), with hand-written serializers/overrides only where semantics demand
(tri-state, secrets, gexps). Phase 1 is escape-hatch-first; codegen is Phase 4.
A mutually-exclusive `raw-city-toml`/`raw-pack-toml` is **not** included
(§13.9).

### 16.14 `define-record-type*` + explicit `->toml` (decided, §13.7)

`define-configuration` buys little here given 16.5 and 16.6. Plain
`define-record-type*` records plus explicit `->toml` procedures (the
`github-actions.scm` style) avoid the `maybe-*`/serializer-symbol machinery and
are more predictable.

### 16.15 Service value ergonomics

Provide a default value and a `(gascity-service-config …)` helper so the common
one-instance case is a record, not a one-element list.

### 16.16 Other details worth specifying

- **File modes:** `GC_HOME`/city dirs `0700`, `cities.toml`/`supervisor.toml`
  `0600`, installed `files` preserve executable bits (scripts).
- **`gc config show --validate` test:** it resolves the city from cwd
  (`cmd/gc/cmd_config.go`); the test must `chdir` into the temp city or use the
  correct path argument.
- **Runtime deps:** `git` is the only propagated dep missing from
  `gascity-next` (verified in `modules/r0man/guix/packages/task-management.scm`);
  also confirm `bash`/`sh` for gate scripts and `gh`/`claude` via `packages`.
- **API bind:** keep the `127.0.0.1` default; a non-loopback bind with
  mutations requires the write-auth fields.
- **Phase-1 pragmatism:** shipping the TOML IR + service plumbing +
  escape hatches first, with typed records as an additive layer, gets a working
  service sooner and de-risks 16.13.

### 16.17 Secrets: never in the Guix configuration; sops-guix via recipe only (decided)

The worked example originally carried `[agent.env] ANTHROPIC_API_KEY =
"$ANTHROPIC_API_KEY"`. That is the design author's own example, not a verbatim
Gas City docs block. The canonical Gas City secret pattern is an abstract
`$VAR` reference in `[upstreams.*]` (`api_key = "$AWS_BEDROCK_KEY"`, see
`docs/guides/configuring-an-agent.md`, "Secrets are never inlined") with the
actual value living in the controller environment or in
`${GC_HOME}/secrets.env` (0600, `docs/getting-started/troubleshooting.md`). It
was removed from the example on purpose: a credential name in a Guix record
normalizes exactly the wrong practice.

**Policy (must be enforced by the service):**

- No literal secret may appear in any record, in the generated `city.toml`/
  `pack.toml`, in `files`, or in the shepherd `environment-variables`. The
  generated TOML may contain only `$VAR`/`${VAR}` references, which Gas City
  expands against the controller environment (`processenv.ExpandSessionEnvValue`;
  agent/workspace env and upstream raw env are expanded, controller-only keys
  are masked).
- The `<gascity-supervisor-configuration>` `environment-variables` field is for
  non-secret configuration only. Document this on the field and add a
  `sanitize`/lint guard that rejects values matching known credential shapes
  (`sk-ant-…`, `ghp_…`, long high-entropy strings, etc.).
- The `$VAR` reference is necessary but not sufficient: the referenced value
  must reach the **supervisor process** environment, because agent sessions
  inherit from it.

**Critical gotcha (verified):** `${GC_HOME}/secrets.env` is read only by Gas
City's own service-file generator (`gc supervisor install` / `gc start`), via
`supervisorServiceExtraEnv` → `supervisorSecretsEnvFileEntries`
(`cmd/gc/cmd_supervisor_lifecycle.go:1380-1512`). The foreground
`gc supervisor run` **does not** load it. Because this service runs
`gc supervisor run` directly under shepherd, the automatic merge will not
happen and the service must load secrets itself, or every `$VAR` reference
resolves empty (a silent provider auth failure).

**Required implementation:**

1. A `secrets-file` field on the supervisor configuration, defaulting to
   `${gc-home}/secrets.env` so it matches Gas City's own convention, with an
   override for sops-guix output. The file is dotenv syntax (`KEY=VALUE`,
   `#` comments, optional `export`/quotes), per
   `processenv.ParseEnvFile`. It must be materialized `0600`, owned by the
   service user, and **never** placed in the store.
2. The supervisor start is a `program-file` wrapper that sources the dotenv
   file into the environment (`set -a; . "$file"; set +a`) and then `exec`s
   `gc supervisor run`. This preserves the `$VAR` resolution path while keeping
   secrets out of the world-readable shepherd service definition.
3. Respect `GC_SUPERVISOR_ENV` for non-provider keys that must pass through,
   matching Gas City's allowlist behavior.

**sops-guix integration (decided: documented recipe only, no code):**

- The manual documents a recipe using `sops-secrets-service-type`/`sops-secret`
  from the `sops-guix` channel
  (<https://github.com/fishinthecalculator/sops-guix>). Secrets are decrypted
  at boot into a ramfs/tmpfs path (typically `/run/secrets`, or
  `/run/user/<uid>/secrets` for a Home environment) and exposed via
  `sops-secret->secret-file`.
- In the recipe the supervisor service **requires the `sops-secrets` Shepherd
  service** and sets `secrets-file` to the decrypted path (or to a synthesized
  dotenv file). Encrypted secrets can be checked into the Guix repo without
  plaintext ever touching disk.
- The channel ships **no** `(sops …)` import and no companion module: a
  `(sops …)` import in `SOURCES` would break the default channel build for
  users without the extra channel. The generic `secrets-file` also serves
  `guix deploy`, a pre-existing `${GC_HOME}/secrets.env`, or any other
  injection path.

Note: the sibling `github-actions` service currently accepts a `token` field in
its record; if that token is a literal, it has the same problem. The Gas City
service must not repeat it.
